# 播放：启动速度与默认编码族

> 从 CLAUDE.md 原样搬出（2026-10-20 精简时）。这里是排查经过、现象和测量数据；CLAUDE.md 里只留现在成立的结论。
> 文中「见『某某』一节」指原 CLAUDE.md 的小节，现在分在 docs/ 下的各个文件里，按标题搜即可。

## 启动速度、预取预热、默认编码族

**`reset()` 里那两个 AVPlay 调用曾经吃掉 570 毫秒，而那条路根本没用 AVPlay。**
`webapis.avplay.stop()` / `close()` 在没东西可停的时候**也不便宜**，它们卡在 playurl
应答和清单之间，每一次 DASH 启动都付一遍 —— 将近一秒的黑屏花在关一个从没打开过的
播放器上。现在按 `obj` 是否存在来判断（它只在 AVPlay 那条路上创建）。到画面从
4148 毫秒降到 3344 毫秒。**这是靠把 `到画面` 那行拆出一个 `teardown` 刻度看出来的，
不是猜出来的** —— 在那之前它只是「playurl 到 manifest 之间有半秒说不清」。

Shaka 还会在启动后 1200 毫秒预热（`Player.prewarm()`）：构建播放器实测约 700 毫秒，
反正一辈子只付一次，那就付在观众看着首页的时候，而不是付在第一个视频的黑屏里。
**脚本本身也不再在 `index.html` 里同步加载（2026-09-28）**：`boot:` 那行量出它 677KB 占了
onload 前 756ms 里的 322ms，挡在一个用不上它的账号选择屏/首页前面。现在 `player.js` 的
`withShakaScript()` 在预热时注入它（通常正赶上观众在选账号），第一次 DASH 起播若来得更早
就排队等；等待期间 `reset()` 挪动了 `mseGeneration`（停了、换了视频），排队的那次起播
丢弃不发 —— 世代守卫，同一个老规矩。日志认 `Shaka 还没加载完，等它` 和
`Shaka 加载完时这次起播已经被换掉，丢弃`。首页那边同时做了两件：选账号屏上就按上次的账号
预取推荐和前 6 张封面（`startBootFeed()`，选中别人则作废），实测选完到首页 585ms → 230ms，
剩下的是渲染。

**光标在卡片上停 0.4 秒，这个视频就被提前问过了（2026-09-28）。** 起因是网页上点下去
画面马上就有。网页快有一半不是软件的功劳：playurl 内嵌在 HTML 里、页面早就碰过 CDN、
开发机链路快两倍多。能搬过来的是前两件 —— `app.js` 的 `prefetchCard()` 在光标停住时发
play() 要发的那三个请求（两条 playurl + `player/v2`），外加对**这张卡片起播时会先开的
那两份文件**（`Mpd.peek()`：默认族顶档视频 + 顶档音频）各发一个 `0-<索引末尾>` 的小
range。play() 取走条目只用一次，预取失败就照常重问，最坏情况等于老路径。限流约束：停住
0.4 秒才发、两次预取至少隔 0.8 秒（1.5 秒时错过过「停在邻居上、挪过来就按」）、每分钟
至多 20 次（10 次当晚在正常浏览里就撞上了，日志 `这张卡片被跳过：撞了每分钟 10 次的上限`）、刚播过的那个不再预取（退出播放光标落回它的卡片上）、有「web 令牌必被拒」教训
的视频不预热（注定 403，正是限流器记仇的那种）、同一文件五分钟内只热一次。**续播点只信
30 秒以内的预取**，否则按下时重问 —— 它是唯一的跨设备新鲜答案，手机上接着看完坐回沙发，
手机那边必须赢。「即将播放」屏一出来就预取排队的那个（倒计时八秒链路本来是闲的），实测
自动续播 `预取=已到（8020ms 前发出）`、1733ms 到画面。**倒计时里把首个视频分段也整段下好（0.5–1MB）试过、没用、已拿掉**：三次自动续播 1452 / 1353 / 1272ms、`loaded→playing` 907 / 782 / 807ms，与不预下的（1278 / 1431ms、~800ms）一样——load() 之后那 ~0.8 秒是解码器出首帧，不是下载。别再以「显然更快」为由把它加回来。**播放中的面板也预取（同晚稍后）**：
播放中按下键、从相关推荐里挑下一个是当晚最常走的路，五次全在 2.5–2.9 秒。只在
`Player.steady()` 时发 —— MSE 在播、没有自救在进行、前方缓冲 ≥20 秒；AVPlay 不报缓冲，
所以那条路上永远不发。几 KB 对播放器一次 0.5–2MB 的分段可以忽略，真正要防的是事故中往
正在拒绝的限流器里再添请求。

**被预热的是 CDN 边缘上的文件，不是连接 —— 第一版就押错了。** 第一版按**主机**预热（每台
主机 20 秒一次、热 avc1 那份），结果两秒前刚热过同一台主机，下一张卡片的第一个响应照样
890ms。`到画面` 里新拆的 `req1→resp1`（第一次去 CDN 的往返）把两类文件分得很干净：边缘
上**有**这份文件 32–74ms，**没有**就 ~900ms，和连接冷热无关。改成按文件之后的对照：预热
请求本身花 1122ms（冷文件），6 秒后播放器对同一文件的第一个响应 38ms。
`respN=…(N个)` 是 load() 之前最后一个响应 —— 冷的那份常常是**第二个**请求（音频或另一份
索引），只看 `resp1` 会被骗（那天第一条就是 resp1=58ms 而 loaded 晚了 1.15 秒）。

| 当天样本 | 预取 | 首个/最后响应 | 到画面 |
|---|---|---|---|
| 冷文件，没预取 | 无 | 902ms / — | 2937ms |
| 冷文件，没预取 | 无 | 46ms / **900ms** | 3012ms |
| 热文件，没预取 | 无 | 38ms | 1609ms |
| 冷文件，预热过 | 已到（6s 前） | 38ms / 53ms | **2466ms** |

剩下的 1.5–2 秒不在网络上：`manifest→req1` 0.4–0.8 秒（Shaka 建 MediaSource、还没发一个
请求），`loaded→playing` 0.8–1.4 秒（第一个媒体分段 1–2MB 加首帧解码）。**一移上去就按
的那次和以前一样**，行尾 `预取=无` 就是这种；`预取=在途（14ms 前发出）` 是门槛 800ms 时
错过的样子，现在是 400ms。

**清单默认族：H.265（2026-08-06 下午回退；08-03 晚到 08-06 之间是 AV1）。**
AV1 当了三天默认族后被观众的眼睛弹劾：一个每个视频都走 av01 的下午，20 分钟内
先后出现**播放中画面变绿**和**解码器整个卡死**——后者缓冲是满的、元素自称在播、
连 `waiting` 都不发，所以卡顿看门狗也看不见它。两个症状都在解码层，都绕过了全部
计数器：当初立的裁判「丢帧数」对这两种病是瞎的，**解错的帧和挂死的解码器都不计入
丢帧**。回退正是当初承诺的那一步（H.265 放回族序第一位），av01 降到 H.265 两个马甲之后：
它仍是 CDN 按文件饿死 hev1/avc1 时的逃生路（08-03 那晚是真的），由失败阶梯的换族档
够到，fnval=2064 也因此保留。
**回退时踩了一个值得记的坑：bilibili 的 H.265 轨有两种盒子。**有的稿件给 `hev1`
（《越狱》），有的给 `hvc1`（当天下午的每一个视频），同一个解码器、两个族名。第一版
回退只把 hev1 提到第一位，hvc1 还压在 av01 后面——于是这些稿件的 hev1 族匹配到
**零个表示**、被无声跳过，av01 顺位再赢，「回退等于没回退」，装完两个视频还是
`编码 av01` 才发现。族序现在是 `hev1 → hvc1 → av01 → avc1`：两种 H.265 马甲都在
av01 前面。判据：`编码` 那行说的是族名，**hvc1 和 hev1 都是 H.265**，看到
`编码 hvc1` 不是异常。以下 08-03 升 AV1 时的记录保留作背景：

**清单默认走 AV1，和官方网页端对齐（2026-08-03 晚起；此前是 H.265）。**
bilibili 每一档都给三份 —— H.264 / H.265 / AV1 —— 而一个 AdaptationSet 是
「播放器可以中途切换的一组等价流」，编码不属于这种关系，所以只能整族选一个。
换成 AV1 优先的理由是 CDN 按文件的区别对待（见限流一节末尾）：av01 文件走的是
官方播放器保活的那条热路径，hev1/avc1 被饿死的那晚它满速。三个前提当晚全部落实：

- **`fnval` 必须带 2048 那一位**（现在是 `2064 = 16|2048`）。fnval 决定响应里
  **有没有** av01 轨 —— 纯 16 的应答只含 avc/hev，av01 优先曾对着一张零条 av01
  的列表空转，devserver 里 `av01Reps: []` 一行抓出来的。HDR/杜比/8K 的位没要。
- **长 codec 串被拒时用 4 段前缀再问一次**（mpd.js `playable()`）。启动行的
  `av01=true` 是短串问出来的，payload 给的是 `av01.0.08M.08.0.110.01.01.01.0`，
  尾巴是色彩元数据不代表解不了 —— 平台探测拒长串会让整族静默消失。
- **「AV1 可能是软解」的顾虑测过了，第一份数据是反例**：设备自测 av01 1080p
  播放加跳转全程 `丢帧=0`。这个计数继续当裁判 —— 真开始丢帧，回退就是把 hev1
  放回族序第一位。**⟶ 2026-08-06 反转：反例之后来了两个正例（绿屏、解码器卡死），
  而且都不过丢帧计数——这个裁判只看得见「来不及解」，看不见「解错了」和「解挂了」。
  回退已执行，见本节顶部。**

H.265 仍是第二位 —— 同画质比 av01 还省 ~15% 字节（628 vs 756 kbps），大量没有
av01 轨的稿件自然落到它。其余约束不变：**够不到 H.264 那一档的族就不要**（用更少
的字节换更小的画面是伪装成优化的降级）；**问不到就只用 H.264**（node 下跑验证
脚本时没有 `MediaSource`）。加载失败且**不是网络原因**时立刻退回 avc1 重来一次
—— 编码探测说了谎的代价不该是一块黑屏。失败阶梯此外还有换族档（不同编码 = CDN
眼里不同的文件）和压一档，见限流一节。另外三道护栏同天补上：`report()` 有令牌桶限速（突发 20 行、之后每秒 1 行，丢弃会在下一行自报），任何未来的循环类 bug 都不再有喂日志风暴和限流器的能力；判别探测已给出 `xhr=403`（整个客户端被拒，多为限流冷却）时跳过注定失败的渐进式镜像轮转，25 秒的黑屏折腾缩到约 8 秒，退出提示也说明白是临时限流。
