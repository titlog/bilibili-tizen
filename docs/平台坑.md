# 在三星电视上做 bilibili 客户端踩过的平台坑

这个仓库的客户端能用，但真正花时间的是搞清楚这个平台到底能干什么。下面每一条都是
在设备上实测出来的，其中好几条推翻了先前的结论。完整的测量记录、日志判据和排查纪律
在 [`CLAUDE.md`](../CLAUDE.md)；这里是给人读的版本，每条先说结论，再说它怎么被发现。

## bilibili 不需要 `Referer`，但会按 UA 拒绝

`api.bilibili.com` 和 CDN 都会拒绝一个它不认识的 `Referer`，却接受完全不带的请求；
同时对 `curl/*` 这类 UA 返回 403。所以规则是：**不发 Referer，发任意浏览器形状的 UA。**

它的后果很大：电视可以直连 bilibili，**不需要局域网代理，也不需要自建后端。**

怎么发现的：用裸 `curl` 试探，每个响应都读起来像「需要 Referer」，据此差点给整个项目
上一个代理。真正的变量是 `curl` 的默认 UA 在黑名单里。永远带 `-A`。

## 这个固件的 widget 发不出 `Cookie` 头

Chromium 120 对 forbidden header 的 `setRequestHeader` 静默忽略，widget 的 `<access>`
策略并不豁免；引擎自己的全局 cookie jar 也灌不进去（跨域封锁）。所以登录态会话
改走 `access_key`：签名后拼进 query，没人剥得掉，也没有「全局一个坑位」可供多个账号
互相驱逐。

怎么发现的：文档里曾断言「这固件允许 widget 设 Cookie 头，设备实测」，而那次实测是在
只有一个账号时做的——`Cookie` 头和 jar 必然指向同一个人，服务器答同一个名字，测量
根本没有区分能力。第二个账号出现的那天它塌了：第二个人扫码登录，信息还是第一个人的。

## 同一稿件手机能放、电视不能，根因是 playurl 的 `platform`

web 端点（`platform=pc`）铸的流令牌会被 CDN 的严格节点 403；app 端点
（`app.bilibili.com/x/playurl`，`platform=android`）铸的被接受——手机 App 就是 app 端点
客户端。`platform` 决定令牌强度，`access_key` 决定档位可见性（不带只给免登录低档），
两样都要。撞 403 时改用 app 端点铸强令牌、自读文件头补 app 端点不给的 `SegmentBase`。

完整排查（含两次把「天气」当诊断的错判与纠正）见
[播放流令牌-app端点根治.md](播放流令牌-app端点根治.md)。

## AVPlay 能播 DASH，但清单必须走 HTTP 到达

`data:` URI 和 `file://` 都被拒，而 widget 没法监听端口——所以 DASH 走 MSE，由
Shaka Player 承担，清单以 `blob:` URL 交给它。同一个原因也回答了「手机投屏为什么永远
搜不到这个 App」：接收端必须在网络上监听，web widget 做不到。

AVPlay 那条路只开放 `COOKIE` 和 `USER_AGENT` 两个流属性，任何需要第三个请求头的设计
都得换形状。`COOKIE` 设成空字符串会让 AVPlay 发出畸形的 `Cookie` 头、CDN 拒绝一切；
而设上真凭证又会把 SESSDATA 明文发给每一台 CDN 主机——流地址是预签名的，正确做法是
**根本不设**。

## 单文件形式封顶 720P，而且有时干脆被拒

`fnval=1` 的 `durl` 最高只到 720P；对有高码率片源的视频，接口照样返回地址，CDN 却在
每个镜像、每个画质上都 403。所以两种形式并行请求，取更好的那个。

## 换 CDN 节点在这条链路上行不通

签名是绑主机的：URL 里带着 Akamai 专属的 `hdnts` 和 `upsig` 一起被校验。八个候选里
七个 403，唯一接受改写地址的那个慢三十倍。**镜像只能排序，不能丢弃**：哪台镜像是死的
属于当天的天气，同一台 cosov 一晚全 403、隔天整晚 206。

## CDN 会按 IP 对突发请求限流

约 20 个请求之后触发冷却，冷却期内连单发顺序请求都会被拒。这就是「有些视频就是打不开」
看起来随机的机制：一次拒绝衍生出二十几个重试和镜像轮转，风暴把限流一直续着。规矩是
被拒之后退避，`load()` 失败隔几秒整个重来。

## 每个 AVPlay 回调都要加世代计数器

`setListener` 注册在 avplay 单例上，`close()` 不解绑，于是一个已经拆掉的会话的
`onerror` 会打进当前正在播的东西里。这件事让「AVPlay 做不了 DASH」这个结论完全反了：
加上守卫后，HTTP 投递第一次就成功。

## 这个 widget 可以自己更新自己

`new Function`、`blob:` 脚本、远程 `script` 标签、`wgt-private` 读写，五条路设备实测
全通。能落盘就意味着更新可以存下来下次直接用，断网时电视照样开得起来。目前只是探测，
没做成产品。

## `web-interface/view` 会答 412

2026-09 起 `/x/web-interface/view` 从这个网络返回 412 的风控 HTML 页，不管 UA、Referer、
cookie；同主机上的 `wbi/view` 不签名就答 200、载荷相同。分 P 列表、简介和强令牌要的
`aid` 全出自这一个调用，静默失败的表现是「按下键面板里没有分 P」。

## UP 主投稿列表：`api.bilibili.com` 的 space 路径有 IP 闸，走 app 协议

`x/space/wbi/arc/search` 是文档上的正路，从这台电视上签了真 WBI（`nav` 领
`img_key`/`sub_key`，混淆表取 mixin，`MD5` 出 `w_rid`）也能答 code=0——**三次里一次**。
2026-09-16 在设备上四轮约四十个请求测出来的：签名版 2/10、3/3、1/3，不签名的
`x/series/recArchivesByKeywords` 2/3；失败是 HTTP 412 页和 `-352 风控校验失败` 交替，
而请求里带什么都不改变比例——挂不挂 `access_key`、加不加 `dm_img_*` 指纹参数、
开不开 `withCredentials`。那是 `api.bilibili.com` 上 space 类路径的 **IP 层闸门**，
不是签名问题，而这个 widget 也没有任何头能加上去过闸（`Cookie` 头出不了引擎，见上）。

同一轮里 `app.bilibili.com/x/v2/space/archive/cursor` **3/3**——手机 app 取同一份列表的
路，签法和 `app.bilibili.com/x/playurl` 已经在用的一样（TV appkey、`access_key` 放进
参数里签）。载荷是 app 的形状：`param` 是字符串形式的 aid，`duration` 是秒，`play` 是
数字，`first_cid` 让起播不用等 `view()`，下一页用 `aid=<最后一条的 param>` 问。
`api.js` 的 `space()` 走的是它。

顺带答了 CLAUDE.md 里悬着的一问：**`web-interface/view` 带不带 `access_key` 都 412**
（各两发，0/2 对 0/2），wbi 孪生端点仍是唯一解。

**⟶ 2026-10-29：孪生端点也会一起 412。** 一台已登录的电视 10-25 和 10-29 打开搜索结果时
`view`、`wbi/view` 都答 412，屏幕上是「打开失败」—— 没 cid 的卡片（搜索、动态、UP 主页……）只能靠
view 起播，日志里连是哪个视频都没有。现在两个都被闸就问**手机 app 的 view**：
`app.bilibili.com/x/v2/view`，TV appkey 签名（和 `rank/region` 一样），按 `aid` 问。aid 不用问网络：
bvid 和 aid 是同一个数的两种写法，`aidOf()` 是 `bvidOf()` 倒过来（九位 58 进制不到 2^53，double
精确；`gated-verify` 拿 app 端给的两对和一串往返卡着）。

10-29 从开发机测（当时这个网络 `view` 412、`wbi/view` 200）：app 端答 code 0，`shape()` 读的字段都在
（标题、简介、UP 主带头像、stat、分 P、时长、copyright、redirect_url），合集在 `ugc_season`，但每一集的
封面、时长直接在条目上（`cover`、`duration`），网页端在 `arc` 里 —— `seasonOf()` 两种都认。没有
`is_upower_*`。**它对充电专属答 -404**（第一次在电视上跑自测，挑中的推荐第二个是充电专属，app 端
playurl 同一秒答 87007）：所以 app 端的 -404 / 62002 写成「也不给」，不让 `API.gone` 读成稿件没了。

答上了之后 30 分钟先问它，它失败就回去问网页端那一对、由它们说了算（稿件没了是它们的话）。**两个
网页端都被闸时 app 端答不答，从这里造不出来**：自测（`--selftest` 里「两个网页端 view 都 412」那几步）
让网页端那一对假装 412、真的从电视上问 app 端（10-29：答上了，356 集的合集读对了），再打开一张没 cid 的
卡片看它出画面。野外真遇到时，`meta:` 那行的 via 或「打开失败」后面的原因会说是哪条路。

**⟶ 2026-10-30：view 答上了却没有 cid。** 越南一台 Tizen 6.0（1.4.12）扫码登录之后，从 UP 主页打开两个
视频（BV1Q64y1k7n3、BV13h411e7U5），`requesting` 那行是 `cid=undefined`、没有分 P，playurl 两种形式都答
`-400 请求错误`，上传的是「拿不到播放地址」。两张卡片都没带 `first_cid`，走的是 view；view 答了 code 0，
但 cid 和分 P 都没有。从开发机（没登录）问：这个 UP 主页只列另外两个视频，`wbi/view` 对这两个都答
62002 —— 多半是只有登录的人看得到的稿件（自己的、审核中的、私密的），**没验证**。当时是哪个端点答的，
日志里没有：`playVideo` 的 view 回调没写 via。现在打开没 cid 的卡片每次记一行
`meta: <bvid> 打开没带 cid 的卡片，<via>`；答上了却没有 cid 就不去要 playurl，屏幕上说「这个视频现在看不了」，
**仍然上传**（原因带 via），B 站到底答了什么还要看下一份。自测里「view 答上了却没有 cid」两步让下一次 view
的回答去掉 cid 和分 P。

强令牌的入口要 aid，`withAid()` 原来只会问 view（10-25 那台：「403 那条路也换不到 aid」）；view 失败时
现在按 bvid 算。

## 没登录时排行和分区页签 `-352`：认 buvid3，app 端排行不认这一套

2026-10-22 到 10-24，四台没登录的电视在「排行」和分区页签（美食、舞蹈、vlog）上报「加载失败：code -352」。
走的都是 `x/web-interface/ranking/v2`，同一分钟里推荐、热门照常回来。登录了的电视从来没撞上过，因为 query 里带着 `access_key`。

10-25 从开发机复现了：几分钟里问了十几次之后，`ranking/v2` 开始回 -352。趁它拦着的时候，在同几秒里穿插着发：

| 请求 | 结果 |
|---|---|
| 不签名 | -352 |
| WBI 签名（`nav` 领钥匙） | -352 |
| TV appkey 签名（加不加 `mobi_app`/`platform` 都一样） | -352 |
| 带 `finger/spi` 发的 `buvid3` cookie | **code 0** |
| `app.bilibili.com/x/v2/rank/region?rid=…`（TV appkey 签名、不带账号） | **code 0，100 条** |

所以这道闸认的是设备身份 cookie，不认签名；而 widget 发不出 `Cookie` 头（见上）。`buvid3` 放进 query、放进 `Buvid` 头也过了
两次，但那之后闸自己放开了，30 个请求连发也没再拦，那两次分不清是 buvid3 起了作用还是闸刚好放开。

app 端排行认 1000 号段的分区号（舞蹈 1004 的第一条和 web 的一样），全站排行是 `x/v2/rank?order=all`。**它时不时回 code 0、一条都没有**，
和分区无关：同样的参数隔两秒连问四次，人工智能 55/55/0/55、户外潮流 0/55/55/55、绘画 55/55/55/0，只有资讯每次都空。
（一开始每个分区只问了一次，以为它有九个分区不认，电视上 vlog 一问就有，才看出是随机的。）条目是 app 的形状：`param` 是 aid，
`name` 是 UP 主，`duration` 是秒，有 `cid`，**没有 bvid** —— `api.js` 的 `bvidOf()` 按网站的算法从 aid 算出来
（对着 web 排行里的 aid/bvid 核对过，`tools/gated-verify.mjs` 卡着）。

`API.ranking` 现在：web 回 -352 → app 端排行，空的隔半秒再问一次；两次都空 → 带 `buvid3`（`finger/spi` 发的，一次运行要一次）再问一次 web；
都不行才是原来那句「加载失败」。每一步记一行 `feed:`，带 buvid3 那一步到底有没有用，等别人电视的日志说话。
**从开发机试这道闸别连发**：开发机和电视是同一个出口 IP。

## 排查纪律：说得通的机制不等于诊断

已经有六次，一个错误被第一个能自圆其说的机制解释、据此设计、然后发布出去，后来被测量
推翻：「CDN 需要 Referer」「AVPlay 看不到 cookie jar」「每条清单路径都失败所以做不了
DASH」「允许设 Cookie 头」「稿件全 403 是天气」「深度跳转打不开是冷缓存」。每一次上一个
解释都仍然成立，也仍然不是原因。

真正管用的动作是**判别实验**：一个实验，两种结果分别指向不同的原因。把 AVPlay 拒绝的
URL 原样交给一个普通的 XHR——`xhr=403` 说明 bilibili 在拒绝这个流，`xhr=206` 说明毛病
在 AVPlay 怎么发这个请求。这个实验现在常驻在每次播放失败里。

另外两条：**跨设备的差异，要抓被质疑那台设备自己产出的证物**；**一个只会在已知选项里
挑的分类器，就是一个会撒谎的分类器**。
