## 怎么在这台电视上调试

零售机上一切方便的手段都是关的，而发现这一点比绕开它更花时间：

| 途径 | 状态 |
|---|---|
| `dlog` / `sdb shell dlogutil` | 什么都不返回 |
| `tizen debug` 的 Web Inspector | 挂起，端口从不打开 |
| `sdb shell` | 直接 `closed`，零售机上读不到应用存储 |
| 三星遥控 WebSocket（`:8002`） | 可用，但第一次连接需要有人站在电视前点确认 |

所以应用自己上报。`app.js` 里的 `report()` 和 `window.onerror` 把内容 POST 到
8099 端口的 `tools/collect.mjs`，`deploy.sh` 会自动接线。

### 怎么建立日志通道

**这是排查一切问题的前提，新开一个会话先做这件事。**

```bash
# 终端 1：收集器，一直开着。它只往 stdout 打，不落盘。
node tools/collect.mjs

# 如果要在会话里反复读，就同时留一份文件：
node tools/collect.mjs | tee /tmp/bili.log
```

几个已经踩过的坑：

- **8099 被占用时 `collect.mjs` 会直接崩**（`EADDRINUSE`），而部署照常成功、
  电视照常上报 —— 上报进了那个孤儿进程的终端，你什么都看不到。先
  `lsof -nP -iTCP:8099` 看一眼；那个进程往往是上一个会话留下的、父进程已是
  launchd 的孤儿，杀掉重开即可。
- **收集器不落盘。** 想事后回读就得自己 `tee`，否则日志随终端一起消失。
- `deploy.sh` 每次会把 `app/js/config.js` 里的 `REPORT_TO` 改写成当前开发机的
  `en0` 地址。**换了网络/换了 IP 就要重新部署一次**，否则电视往旧地址发，静默
  丢弃。
- 收集器没开时，`report()` 静默无操作。**不会有任何提示。**
- **它现在会自愈，但要等最多五分钟（2026-08-12 改）。** `report()` 连撞五次失败
  仍然停止拨号（防的是电视整晚对着一台已经下班的笔记本重拨），但改成**睡而不是
  死**：五分钟后放一行出去当探针，通了就全额恢复，不通就再睡五分钟。代价是没有
  收集器的一晚上每五分钟一个 3 秒超时的 XHR，而且只在有事件发生时才会发 ——
  `report()` 由事件驱动，闲着的电视一行都不发。
  **此前它是永久关闭的，这条 2026-08-12 收了账**：收集器整天开着，电视中途待机、
  唤醒时网络慢了几秒，五次全撞在那个缝里，之后这个进程再也不上报 —— 19:00 一次
  播放失败连一个字都没留下，而同一时刻 `curl` 打收集器是 200。当时唯一的解药是
  重装。**判别方法没变**：重装后 `engine:` 和 `account:` 会在几秒内自己出现，
  没出现才是真的通道有问题；`curl -X POST .../report` 落不落盘，分开的是「收集器
  死了」和「电视不发了」。
- 光在电视上退出再打开**未必**能重置它 —— Tizen 常常是挂起而不是杀进程，JS
  上下文还在，计数器就还在。等五分钟的自愈，或者重新部署（立刻生效）。

### 每次启动就有的几行

不需要 `--selftest`，任何构建都会上报：

```
engine:  Mozilla/5.0 (SMART-TV; LINUX; Tizen 9.0) … 120.0.6099.5 | ES6=true | MSE=true | Blob URL=true …
account: 4 个账号，当前 route=access_key，服务器认得 <用户名>
whoami:  启动 活动=a4 access_key=有 header=有 1ed07418 jar主=无 withCred=否 | a1 mid=… 凭证=…
whoami:  启动 常规                        → isLogin=true mid=<mid> uname=<用户名>
whoami:  启动 只有 Cookie 头·不带 access_key → isLogin=false
whoami:  启动 裸请求·什么都不带              → isLogin=false
```

第一行让「引擎太老所以不能用 X」这类论断无处藏身；`account:` 说明哪条路径承载了
会话、以及服务器认不认。

`whoami:` 那三行是**常驻的判别实验**，登录成功时也会再跑一遍（`whoami: 登录后 …`）。
它们分别问：「现在这套配置能不能把被选中的账号送到服务器」「`Cookie` 头自己能不能」
「引擎背着我们有没有自己的会话」。**账号层历史上最贵的一次错误，就是用一个三条路
都会给出同一个答案的观测去断言其中一条成立**（见「一台电视，好几个人」）——
这三行的存在就是为了让那种断言不可能再成立。读的时候看 **mid 对不对得上**，
不是看认不认得出人。

### 播放相关的日志，以及各自能回答什么问题

| 日志行 | 回答什么 |
|---|---|
| `BV1xxx 标题 cid=… P7/24 — requesting qn=80` | 是哪个视频、**哪一 P** —— 分 P 稿件上光有 bvid 分不出「P10 打不开」和「P10 悄悄开成了 P1」。没有 `P几/共几` 后缀说明播放时手里根本没有分 P 列表（走的是卡片自带 cid 那条快路，`resumeCid()` 没参与）；`P?/24` 说明 `resumeCid()` 给回了一个不属于这个稿件的 cid |
| `dash offers qn=80 accept=…` / `progressive gave qn=…` | 两种形式各自能给什么，路由为什么这么选 |
| `编码 hev1` | 这一条流实际用的编码族；后面跟「（指定）」说明是失败退回来的 |
| `到画面 按下起=… playurl=… teardown=… manifest=… req1=… resp1=… respN=…(N个) loaded=… playing=… \| 预取=… 预热=…` | 启动时间的分解，毫秒。**`按下起` 才是观众等的时间**（2026-10-20 加，只在第一次出画面时有）；后面的刻度从这一段播放器起步算，走过强令牌的 `到画面(强令牌)` 会从重建重起，前面摸索的几秒不在里面。**动启动路径之前先读它**；`req1→resp1` 是第一次到 CDN 的往返，`respN` 是 load() 前最后一个响应，行尾说光标停留那次预取/预热用没用上（见「光标在卡片上停 0.4 秒」）；一个视频只打一行（`playing` 事件在每次拖动后都会再触发，而刻度只记第一次，以前同一份数字会重复打四五遍）。兜底和原地重启各有自己的时钟：`到画面(兜底)` 从 `downgrade()` 起算，`到画面(重启)` 从重启起算 —— **兜底路径上不带后缀的那行仍然是 AVPlay 的假 playing 事件**，读带后缀的 |
| `播放中出错（…），从 mm:ss 用 DASH 原地重启` / `原地重启后仍然出错，退出` | 播放中途的终止性错误。以前这里是「保持不动」—— 一行日志加永久冻屏；能走到这一步的错误全是终止性的（世代守卫早已滤掉迟到的假错误），媒体元素出错后就是死的。现在原地重启一次（优先 DASH、从当前位置），第二次有声退出。**预算按事故计，不按视频计**（2026-08-03）：重启点之后真实前进 90 秒就把额度补回来 —— 之前花掉就不再有，13 分钟处一块坏区用掉它，18 分钟处的下一块就把一个本来还能看的视频整个退了出去。解码重载（60 秒回血）和 shaka 严重错误重取（同样 60 秒）同理 |
| `渐进式换镜像重试 N/M` / `所有路都试过，有声退出（…）` | 错误处理里原本的两个哑出口，2026-08-06 起说话。前者是渐进式镜像轮转在走（AVPlay 每台要 6-20 秒才失败，黑屏时间的常见去处）；后者是最终 toast 退出。以前观众看到提示而日志一片空白——13:44 那个「shaka load 失败之后静默 60 秒、然后凭空一条新 requesting」的谜，就是这两个出口连起来的：静默轮转、静默 toast、观众自己重按 |
| `卡死且没有别的镜像可换，跳过同族重载，直接换编码族` | 同族重载这一档在「一个字节都没来 + 轮转无处可去」时被跳过（2026-08-09 起）。它修的是**截断**（掐线留下空洞，换台主机重问能补上）；字节根本不来、又只剩一台主机时，它就是同一份文件、同一台主机、同样的问法——20:17 花二十秒证明过一次。**注意反面教训：不要因此认定「阶梯抛弃过的族是坏的」**，同一晚 20:18 的数据说得很清楚——病的是 854 秒附近那段字节，不是 av01 这份文件（avc1 的 360p 档在 869 秒同样被 403），换回 av01 从 869 秒一路顺畅。族和字节区间是两件事 |
| `解码失败（…），从 Xs 用 … 原样重载一次，镜像改从 … 出发` | 解码错误十有八九是穿马甲的网络错误：CDN 掐线被引擎当成正常收尾，半截分段喂进解码器才报 error 3。重载前把每个表示的镜像轮转一位，让重试换一台主机出发 —— 同主机重试对确定性截断是零胜率，2026-08-03 整晚验证。轮转跳过 403 黑名单里的主机；两台都各有各的病时它会留在原主机上，这是诚实的答案 |
| `镜像 … 返回 403，这个视频内不再排在前面` | 这台主机进了本视频的黑名单。Shaka 对 401/403 不做 BaseURL 转移（当场判死），所以只能由我们保证它不再站到清单第一位。按视频清空，不跨稿件记仇 |
| `排头镜像 403 已拉黑，立即换镜像重建清单` | 轮转赌上了一台没测过的死镜像。拉黑后允许立即重建，preferGoodHosts 换排头 —— 没有它，一个 403 曾把整个梯子一秒烧到 720p。**界限是「学到新坏主机」而不是每次加载一次**：旗标曾误declare在每次重建自己的会话里，一个全主机被拒的稿件以每秒 3 次原地重建，转圈之外还把请求风暴喂给限流器，把一次抖动续成了「所有文件都 403」（22:38 实录，连累了后续无辜视频）。N 台主机至多重建 N 次，之后 403 落进换族分支 |
| `换 AV1 的同画质（不同的文件…）` / `AV1 档不可用（av01 表示 N 个、带段索引 M 个…）` | 换族档打起来了，或者说清了为什么打不起来：0 个是 playurl 没给（查 fnval），非 0 是 isTypeSupported 拒绝或够不到 avc1 基线。av01 是默认族时这一档自动跳过 |
| `沿用 N 分钟前的教训：编码从 … 出发，坏主机 X，坏文件 Y` / `这条路稳定播了一分钟，记为本视频的教训（…）` | 按视频的教训存储（2026-08-09 起，`bili.lessons.v1`，设备级）。重进病视频不再从头重学：赢的编码族、坏主机、坏文件、渐进式败绩都按 cid 记住，**六小时过期**——这是设计不是省事，按文件的天气隔晚必翻（08-06 av01 是病、08-09 av01 是药），昨天的教训是谎言。编码教训是**软偏好**（领跑族序、绝不锁死，族不在了自动落回默认序）。**「赢的族」按「任何一次自救之后稳定播满一分钟」记，不挂在解码阶梯的预算回血上**——上线当晚就踩到：19:56 那场事故是三档 hvc1 文件挨个 403、被逐个剔除直到整族用尽落到 av01，全程没碰解码阶梯，于是坏文件记住了、赢的族丢了。记录上限 100 条，最旧先淘汰。**回放的坏文件按教训自己的年龄计龄，不是永久**（2026-08-11 修）——原来回放时写的是 `true`，而 `true` 在过期判断里的意思是「永不过期」，于是本次会话学到的坏文件 5 分钟作废、从教训回放的（最长六小时前）却在整个视频内永久有效，两条路互相矛盾而生效的是基于更旧证据的那条。当晚 20:07 一次失败学到 9 个坏文件，七分钟后把 av01 整族从清单删空（日志写着 `AV1 档不可用（av01 表示 0 个）`），而同一分钟逐个探这个稿件：avc1/hvc1 的 480P、360P 和 av01 的 480P 全 403，**只有 av01 活着**——教训说对了族，名单让它没法兑现，观众拿到「所有路都试过」。修好后同一个视频 2.6 秒出画面、1080P av01。日志认括号里那个数：`坏文件 9（还在保鲜期内的 0 个）`。六小时保留期继续为「赢的族」和「渐进式败绩」服务，那两样不按分钟翻脸 |
| `文件 …-1-30066.m4s 被 403，从清单剔除，从 Xs 原地重建` | 按文件的 403 黑名单（2026-08-06 起）。403 常常瞄准一份文件而非一台主机——当天 15:54 一个视频的 hev1-720p 文件全主机 403 而 1080p 健康，原地重启重建同一张清单，ABR 每次恢复都下探踩回同一颗雷，三轮烧光预算有声退出。现在学到新坏文件就把那个表示剔掉重建（同视频内记住，preferGoodHosts 式地在每次建清单前重放；「学到新的才重建」封顶次数）；族的顶档被剔会自动过不了 avc1 基线检查、整族让位，都是 chooseVideos 原有规则的自然结果。**名单条目 5 分钟过期**（`BAD_FILE_TTL`）—— 按文件的 403 是分钟级天气，永久拉黑会让一次抖动把一份好文件锁到本视频结束。剔到清单为空时不认输：`坏文件名单把清单掏空了，这次忽略名单重建` —— 空清单等于放弃，而名单本身可能已经过时 |
| `指定的 hvc1 剔掉坏文件后够不到基线，放开族的限制，改用 av01` / `坏文件名单已经忽略过两次还是掏空清单，不再原地重建，交给上层` | 剔坏文件那一档的死循环（2026-09-28 22:07 修）。BV1GAY56VEg9 的 1080P hvc1 文件这台电视每次都解不过第 3 秒（字节 206、60ms、完整，`code=3014` 或「卡住 14 秒无进展」）。剔文件那档重建时**锁着 hvc1**，而剔掉顶档之后 hvc1 够不到 avc1 的基线 → 清单空 →「坏文件名单把清单掏空了，这次忽略名单重建」清空名单 → 同一份文件回来 → 再卡、再剔（名单刚清空，「剔过」的记录也没了）→ 每 20 秒一圈，黑屏，重开视频也一样。现在锁定的族被掏空时先放开族的限制（换族 = 换文件，正是剔它的本意），忽略名单每视频至多两次，再多就 emit error 交给 app.js 的兜底与有声退出。**同一个视频两分钟后又撞上 web 令牌 403**，强令牌的两阶段读文件头按 hvc1 先读——而 hvc1 顶档正是那份坏文件，剔掉之后 hvc1 只剩 720P、avc1 一份头都没读、基线是 0，于是 720P hvc1 过关、1080P avc1 没机会。现在 `Player.badFilesFor(cid)`（本会话 + 保鲜期内的教训）传给 `playurlDashStrong`，选先读哪个族时把坏文件排除在外，坏文件本身也不读。这一条只做过离线推演：它要「web 403 + 顶档解不了」同时发生，当晚没再复现 |
| `判别探测 xhr=206 131072B 235ms 偏移=55MB(685s) 主机=… 档=80 avc1` / `最后一个分段请求 bytes=0-1112 要 1113B 收到 1113B（完整）` | DASH 这条路的判别实验，和 AVPlay 那边的 `probe:` 同一个套路，晚了很久才有。卡住或解码失败时，拿同一个地址、同一个偏移用普通 XHR 再要一次字节；同时报出最后一次分段请求要了多少、实际到了多少。**它分开的是三件长得一样的事**：`xhr=206` 而分段「短了」→ 真的是掐线留下半截；`xhr=206` 而分段「完整」→ 拿到的根本不是媒体数据（403 的 HTML 错误页被喂进了解码器，2026-08-09 就是这个）；`xhr=403`/`连接失败`/`十秒无响应` → 地址或主机的问题，与解码无关。本文件长期声称「解码失败十有八九是穿马甲的网络错误」，这两行是第一次真去量它 |
| `分段请求 发出=214 回来=214 在飞=0 最后一次发出=12.3s前 最后一次回来=12.3s前` | 卡住的时候**还有没有人在要字节**。**这四个数按「会话/清单」计，每次 `load()` 前清零** —— 被中止的请求（跳转、换档、重建）只加「发出」不加「回来」，不清零的话 `在飞` 会永久往上漂，一个正常跳转就足以让它谎报「连接吊死」。08-15 首次上线时漏了这个复位，当晚审查抓出来；那份样本本身没被污染（三次重建之间是 6→7→7→7 而不是 6→12→18，说明确实是同一批吊着的请求），但那是运气不是设计。这是「线路哑了」和「我们自己哑了」的分界，而且**不靠配对**（配对正是 08-15 出错的地方）：`发出==回来` 且最后一次发出在十几秒前 → 没有请求在飞，Shaka 停止索取，毛病在这一侧，立刻重建是对的；`发出>回来` 且最后一次回来在十几秒前 → 请求发出去没人应，连接吊着或 CDN 坐着不动，这时才轮到退避。两者要的修法相反 |

### 无人值守跑全流程

`zsh tools/deploy.sh --selftest` 会派发和遥控器一样的按键事件，把整条流程走一遍
—— 网格、播放、面板、滚动、拖动、跨缓冲区远距离跳转、暂停、恢复、退出、账号页
—— 并逐步上报。这是**唯一**能在无人值守下检验一个构建的办法，也是让回归在到达
沙发之前就被抓住的办法。**只要某个 bug 能靠按顺序按键复现，就给它加一步。**

跑完最后一行是 `SELFTEST 结束，全部通过` 或者 `结束，N 步失败`。注意它会自动
播放视频，正在看片时别跑。看片用的构建也**绝不要**留着 `--selftest`。

## 别人电视上的诊断日志（2026-10-21，`diag.js` + `server/`）

**为什么有它。** #5：一台 Tizen 3.0 的电视，封面、登录都好，每个视频都报「视频流被拒绝（403）」，一小时后还是。

它拿到了哪些主机、每条路各自是什么状态码、强令牌有没有走到。
