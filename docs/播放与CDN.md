# 播放与 CDN：测定的事实、限流、令牌

> 从 CLAUDE.md 原样搬出（2026-10-20 精简时）。这里是排查经过、现象和测量数据；CLAUDE.md 里只留现在成立的结论。
> 文中「见『某某』一节」指原 CLAUDE.md 的小节，现在分在 docs/ 下的各个文件里，按标题搜即可。

## 已经测定的事实

以下结论来自 2026-08-01 和 08-02 的实测，其中好几条推翻了项目最初的假设 ——
包括这份文档自己断言了很久的一条。**不要凭直觉重新推导，也不要相信这里任何一条
没有附带测量的说法。**

**bilibili 不需要 Referer。** `api.bilibili.com` 和 CDN 都会拒绝它不认识的
Referer，却接受完全不带 Referer 的请求；它们同时会对 `curl/*` 这类 UA 返回 403。
所以规则是：**不发 Referer，发任意浏览器形状的 UA**。在 widget 里就是
`index.html` 的 `<meta name="referrer" content="no-referrer">` 加上
`avplay.setStreamingProperty("USER_AGENT", …)`。这条的后果很大 —— 电视直连
bilibili，**不需要局域网代理，也不需要自建后端**。

> 永远不要用裸 `curl` 去试探 bilibili。它默认的 UA 在黑名单里，于是每个响应都
> 读起来像「需要 Referer」，你会据此断定项目非上代理不可。这个假信号已经吃掉过
> 一整个晚上。**永远带 `-A`。**

**这一代三星电视必须用三星发行的分发证书。** Tizen 自带的分发证书一律
`Invalid certificate chain` —— 2022 年过期的那套和有效期到 2032 的 `-new` 那套
都一样，所以这是信任链问题，不是过期问题。VS Code 的 `tizentv` 插件签不出三星
证书，Tizen Studio 自带的任何 CLI 也签不出。

**AVPlay 只开放 `COOKIE` 和 `USER_AGENT` 两个流属性。** 渐进式播放没有通用的
自定义 HTTP 头，任意头只存在于 `setDrm()` 那条 DRM 授权路径上。任何需要第三个
请求头的设计，都得换形状。

**把 `COOKIE` 设成空字符串会直接搞坏播放。** 纯 cookie jar 的会话读不到
SESSDATA，于是 `Auth.cookieHeader()` 返回 `""` 而 `isLoggedIn()` 是 true。把它
交给 `setStreamingProperty("COOKIE", "")`，AVPlay 会发出一个畸形的 `Cookie` 头，
CDN 拒绝一切。表现和「这个流坏了」一模一样，而且只在用户登录之后才开始出现。
**只在确实有东西可发时才设这个属性。**
**⟶ 2026-09-07 起干脆不设它。** 流地址是预签名的，AVPlay 不需要会话（本文档早就这么写），而设上去的是 `SESSDATA; bili_jct; DedeUserID`，会发给渐进式那条路打开的**每一台**主机，包括镜像轮转几次之后轮到的 `http://` 孪生 —— 账号凭证明文进 Akamai 和 PCDN 节点。官方网页播放器也不这么做：它的 cookie 只作用于 `.bilibili.com`，CDN 主机在别的域名上。上一段的教训仍然成立，方向相反：**空字符串**搞坏一切，**不设**才是 spike 里实测渐进式能播的那个状态。

**播放路径，全部在设备上实测过。**

| 路径 | 可用 | 备注 |
|---|---|---|
| AVPlay + 渐进式 `durl` | 是 | 原生缓冲、原生 seek、内存恒定 —— 但受下面的画质上限所限 |
| `<video>` + MSE | 是 | 这里播 DASH 的唯一途径，现由 Shaka 驱动；`avc1`/`hev1`/`hvc1`/`av01` 与 `mp4a.40.2` **全部**过 `isTypeSupported`（2026-08-02 设备实测，见启动那行 `engine:`） |
| AVPlay + HTTP 上的 MPD | 是 | 证明我们生成的清单本身是合法的 |
| AVPlay + `data:` URI 的 MPD | 否 | `PLAYER_ERROR_INVALID_URI` |
| AVPlay + `file://` 的 MPD | 否 | `PLAYER_ERROR_NOT_SUPPORTED_FILE` |
| AVPlay + 裸 `.m4s` | 是 | 能解，但只有画面，没有音轨 |

AVPlay 的 DASH 实现是对的，它只是坚持清单必须走 HTTP 到达，而 widget 没法监听
端口。所以 DASH 走 MSE —— 由 Shaka 承担，清单以 `blob:` URL 交给它，不需要任何
服务端。

**单文件形式封顶 720P，而且有时干脆被拒。** 这条决定了播放器的架构：

| 形式 | 能给什么 |
|---|---|
| `fnval=1`（`durl`） | `accept_quality` 最高只到 `[64, 16]` |
| `fnval=16`（DASH） | 同一个视频给 `[116, 112, 80, 64, 32, 16]` |

所以先问渐进式，等于把**所有**视频都按 720P 播，不管片源多好；而对于有高码率
片源的视频，API 仍然会返回一个 durl，但它的 CDN **在每个镜像、每个画质上都返回
403** —— 表现出来就是「有些视频就是打不开」。`app.js` 现在**两种形式并行请求**，
取更好的那个。**打平时 DASH 胜出（2026-09-28 反转，此前是渐进式）**：「AVPlay 是原生的」
在手写字节泵的年代值很多，换成 Shaka 之后 DASH 起播 1.6–3 秒、带着整套自救阶梯，而 AVPlay
一次拒绝要白等 6–8 秒才报 —— 当晚 BV1t441167uj 的 1080P durl 与 DASH 顶档打平，按下到画面
11 秒，其中 8 秒是 AVPlay 败在一个判别探测读出 `xhr=403` 的地址上。按视频的「渐进式败绩」
教训只救得了**第二次**进这个视频。渐进式现在只在严格更好时胜出，另外仍是 DASH 全灭后的最后一手。

### DASH 是 Shaka 的事，不是我们的事

`Mpd.build()` 用 playurl 已经返回的东西写出一份 MPD 清单 —— 各档表示、编码、
init 段和分段索引的 `SegmentBase` 字节区间 —— 然后
`app/vendor/shaka-player.compiled.js` 以 `blob:` URL 播放它。分段索引的解析、
请求大小、缓冲区回收、跳转时中止在飞请求、被拒后重试、画质自适应，全部是 Shaka
的事。

这套东西替换掉了一版手写的 MSE 字节泵，原因值得留档：**下面每一条都曾经是那个
泵的 bug，而且全部是在一天之内暴露出来的。**

| 症状 | 原因 |
|---|---|
| 续播要等很久，几十 MB 下下来又被丢掉 | 读取游标从字节 0 开始，而 `currentTime` 已在续播点，中间下到的全被回收 |
| 往回跳转直接被拒 | 没有时间→字节的映射，因为从没解析过 `sidx` |
| `video element error 3`，视频降档重启 | 换偏移续读却没调 `SourceBuffer.abort()`，解析器还停在上一段流中间 |
| 播几分钟后彻底不动 | 把短响应读成了文件结束；这个 CDN 把单个 range 截断在 2 MB |
| **只要快进，之后就再也加载不出来** | 跳转没有中止在飞的 XHR，按几下就把这个引擎给单主机的六个连接耗尽了 |
| 音轨领先画面 66 秒而画面饿死 | 两条轨的预读之间没有任何耦合 |

Shaka 一条都没有，而且不是勉强打平：同一条链路上它估算出 14 Mbit/s，手写泵只
跑到 5.8；自检里的深度跳转步骤也全过。

配置里这几项是量出来的，不是凭口味定的：

- `abr.defaultBandwidthEstimate: 6000000` —— Shaka 自己的默认值太保守，第一个
  视频会先起 720P、一秒后再切上去，白下载并丢弃一个分段。到画面的时间：
  4.8 秒 → 3.0 秒。
- `rebufferingGoal: 1` —— 设成 2 的那一秒，是在 `load()` **已经完成之后**多出来
  的两秒黑屏。
- 重试跨度约十秒（`maxAttempts: 7, baseDelay: 600, backoffFactor: 1.6`）。这条
  改过两次方向，见下面的限流一节：一开始按参考实现用了平坦短延迟，但那对付的是
  单次断连；这个 CDN 的拒绝是以秒计的冷却，1.5 秒的重试窗口全落在冷却里。
- 播放器**只建一次，反复复用**。构造加 attach 要约 700 毫秒，每个视频都付一次
  就是 700 毫秒的纯黑屏。`load()` 和 `unload()` 串在同一个 promise 上排队 ——
  让它们竞争会把媒体元素留在什么都播不了的状态；而且 Shaka 持有这个元素期间，
  `reset()` 绝对不能去动 `src`。
- `Mpd.build()` 拿 `PREFERRED_QN` 当天花板，写出的画质阶梯到 1080P 为止。这样
  自适应才有**向下**的余地，而这正是深度跳转进一个超长视频还能活下来的原因。

> 时间数据来自每个构建都会上报的 `到画面` 那一行：
> `playurl=… manifest=… loaded=… playing=…`，单位毫秒，从按下按钮算起。
> **动启动路径之前先读它。** 有两个「显然更快」的改动 —— 把索引请求并进第一个
> 媒体块、以及用递增退避 —— 实测都更慢。

### 换 CDN 节点在这条链路上行不通（已实测，别再推导一遍）

换 CDN 节点的那几个油猴脚本（CCB、Bilibili Accelerator、Bilibili Video CDN
Switcher）做法都一样：保留签名 query 原样，只改主机名。2026-08-02 从这个网络对
九个 upos 节点、分别用主地址和备用地址的签名试过：

- 八个候选里有七个返回 **403**。签名是绑主机的：URL 里带着 `os=akam` 和 Akamai
  专属的 `hdnts=exp=…~hmac=…`，和 `upsig` 一起被校验，换主机就对不上。
- 唯一接受改写地址的 `upos-sz-upcdnbda2` 跑 0.14 MB/s，而原节点是 4.5 MB/s ——
  慢三十倍。
- **bilibili 自己给的备用地址**（`upos-sz-mirrorcosov`）原封不动、在它自己的
  主机上也返回 403。所以镜像轮转会把请求浪费在一个从一开始就是死的镜像上，这也
  是当初一次拒绝会连锁成一片的部分原因。
  **⟶ 2026-08-03 这条反转了，见下面限流一节的「镜像只排序、不丢弃」**：同一台
  cosov 整晚 206，而 akam 主节点整晚间歇掐连接。两天两个方向 —— 哪台镜像是死的
  属于**当天的天气**，不是可以写死进代码的事实。

原本的 Akamai 主节点就是这里能达到的最快节点，没有更快的可切。**登录与否毫无
区别** —— 用登录浏览器拿到的真实 1080P 地址（`id=80`，3.0 Mbit）重跑一遍，同样
那七个节点 403，`upcdnbda2` 通过但只有 0.44 MB/s，原 Akamai 主机 12.2 MB/s。

**12.2 MB/s 这个数字值得记住，因为电视差得远。** 同一网络、同一主机、同一文件：

| | 速率 |
|---|---|
| 开发机，单流 | 12.2 MB/s |
| 电视，最好的持续速率 | 5.8 MB/s |
| 电视，冷连接的第一块 | 0.93 MB/s |

所以启动延迟剩下的部分是**电视自己的链路和 HTTP 栈**，不是 CDN，也不是客户端的
请求方式。路由器管理页确认过：电视在 5 GHz 上，RSSI −43、SNR 47，是全屋信号最好
的设备，但协商速率只有 433 Mbit —— 那是 802.11ac **单空间流**的典型值，这台机器
的 Wi-Fi 模块就是 1×1 的，换位置换频段都改不了。而 433 Mbit 的链路本该给出
150–200 Mbit 的 TCP 吞吐，电视实测最好只有 46 Mbit。**所以插网线大概率帮助
有限，瓶颈在这台机器的软件栈。**

### CDN 会按 IP 对突发请求限流，冷却期让「有些视频就是打不开」看起来很随机

2026-08-02 从开发机对一个 `upos-hz-mirrorakam` 地址实测：

| 方式 | 结果 |
|---|---|
| 顺序单个 range 请求 ×3 | `206 206 206` |
| 4 个并发 range 请求 ×3 轮 | 一半返回 `000` —— 连接被掐断，拿不到状态码 |
| 累计约 20 个请求之后，任何方式 | 每批只有一个成功，其余全被拒 |

最后一行才是关键：**一旦触发，冷却期内连单发顺序请求都会被拒。** 它不是按 URL
也不是按视频，而是这个客户端在短时间内要得太多。

这就是应用真正表现出来的那个故障的机制：一个视频第一个 range 成功、第二个被拒，
紧接着**下一个视频也垮掉**。当初一次拒绝会衍生出另外二十几个请求 —— 四个「镜像」
其实是两台主机各列两遍、立刻重试、然后整个视频换另一种形式从头重启、再垮一次。
这场风暴把限流一直续着。

所以这里的规矩是：

- **被拒之后退避，给冷却期留时间。** Shaka 的重试跨度是七次、约十秒。它自己的
  默认值（1.5 秒内六次）整个落在冷却窗口里，次次失败，然后把一个好端端的视频
  判成不可播。
- **`load()` 因网络类错误失败时，隔几秒把整个加载重来一次。** 日志里认这一行：
  `首次加载被拒（…），3 秒后重来一次`。
- **不要给 DASH 那条路 http:// 镜像孪生。** 它们是为 AVPlay 那套老旧 TLS 栈准备
  的；对任何现代客户端来说那就是同两台主机再列一遍，轮转一轮等于每台打两次。
- **镜像只排序、不丢弃（2026-08-03，这一条曾经写反）。** 08-02 实测 cosov 在每个
  视频上都 403，于是 `api.js` 把它整个丢掉；08-03 晚上 akam 主节点开始间歇性掐
  连接（`shaka 1002`、空状态码），电视手里的清单只剩一台孤主机，同一段 range 重试
  七次次次撞死，「越狱 P17」在同一秒上墙了一整晚 —— 而**同一小时、同一文件、同一
  局域网**，官方网页播放器靠转移到 cosov（206）毫发无损，桌面浏览器抓包和用同款
  hev1 文件直接探字节都证实了。丢一台镜像的代价不是当天暴露的：它风平浪静地跑了
  一天，然后在主节点变天的第一个晚上把每个 1080p 视频变成地雷。现在 `mirrors()`
  的规矩是**排序**（主节点 → cosov → mcdn/szbdyd），`tools/mirrors-verify.mjs`
  卡发布；Shaka 会沿多个 BaseURL 自动转移 —— 把死主机排第一位、真主机排第二做过
  实证，`load()` 照样成功。解码失败重载时 `player.js` 还会把镜像轮转一位再重建
  清单（`镜像改从 … 出发` 那行日志），对付的是「掐线被 Tizen 当成正常收尾、半截
  数据引爆解码器、同主机重试永远复现」这个确定性死循环。
  **但 Shaka 对 401/403 不做镜像转移** —— 它把这两个状态判成 CRITICAL，当场放弃，
  不像掐线那样顺着 BaseURL 列表试下一台（当晚实测：一个稿件 akam 截断分段而 cosov
  整个 403，盲轮转把 cosov 排到第一位，每次重载死在 `load()`，解码阶梯一步没走
  就漏到退出）。所以 403 过的主机会进本视频的黑名单（`镜像 … 返回 403，这个视频
  内不再排在前面` 那行），轮转跳过它，每次重建清单前 `preferGoodHosts()` 都保证
  第一位不是它。黑名单按视频清空 —— 哪台镜像是死的按稿件各不相同，同一晚两个
  方向都发生过。
- **手里已经有 DASH 清单时，渐进式第一次失败就换路，不再轮转镜像**
  （`app.js` 的 `dashWaiting`）。轮转是给「渐进式是唯一出路」准备的：AVPlay 每次
  约 6-7 秒才失败，三个镜像就是 20 秒黑屏，而其中两个（http 孪生、以及可能正赶上
  它死的那天的 cosov）胜算很低 —— 更要紧的是，**第一次探测的 `xhr=206` 已经说明
  地址和网络都没问题、是 AVPlay 发不出去，那么换台主机让同一个播放器用同样方式再
  问一遍，修不了它**。`decide()` 把 DASH 响应留在会话上（两种形式本来就并行请求
  过），`downgrade()` 直接复用，省掉一次往返。设备实测同一视频前后对比：按下到
  `switching to dash` **21 秒 → 6 秒**，探测请求 3 个 → 1 个。
  代价：1 号镜像抖动、2 号本可成功、而 DASH 恰好是坏的，这种组合现在会输 ——
  没观测到过，记录的模式一直是反过来的（渐进式 403 而 DASH 正常）。

**`Referer` 和 `Origin` 与这些 403 无关，`fetch` 和 `XMLHttpRequest` 的区别也
无关。** 对同一个 URL、在同一时段、在浏览器已经成功取过它之后测的：

| 请求方式 | 结果 |
|---|---|
| 浏览器 `fetch`，从 bilibili 页面发出 | 206 |
| curl，不带 Referer 不带 Origin | 206 |
| curl，带 `Referer: https://www.bilibili.com/` | 206 |
| curl，带 `Origin: https://www.bilibili.com` | 206 |

而几分钟前对**另一个**、浏览器从没碰过的 URL 用同样三种 curl 组合，次次 403。
所以变量不是请求头也不是客户端，**是最近问了多少、问得多急**。不要再靠「加个
Referer」来重新论证这件事，试过了。

> 从开发机测这件事会触发同一个限流，然后电视上的播放会因为和电视毫无关系的原因
> 失败。**探测要节制**；当某个视频在你跑完一轮 `curl` 之后开始失败，先怀疑这个。

### 传输形状：看起来是**排队**，但那是**竞争**不是链路上限（08-15 首测一半，08-16 拿到另一半，结论因此翻了）

「MSE 走同代 Chromium 栈，大概率也是 h2（未在设备上证实）」在这份文档里挂了很久，
而 08-15 下午一场持续十几分钟的卡顿（每 10–15 秒一次看门狗出手，跨三个编码族、两台
镜像、web 与 app 两种令牌，`丢帧=0`，八次判别探测全 206）逼着去量它。两个办法：

- **`PerformanceResourceTiming.nextHopProtocol` 问不出来。** 138 条记录全是空串 ——
  跨域响应不给 `Timing-Allow-Origin`，这个字段就被扣着。`?` **不等于 1.1**，日志里
  那句「问不到协议」就是为了不让下一个人把它读成 1.1。**别再试这条路。**
- **主动实验能问出来**：同一个流地址、同时发 8 个 1KB 的 range（`probeTransportShape`）。
  设备实测：`发出(ms)=0,2,4,6,8,10,13,16`（八个在 16ms 内全部发出，**本机发送开销
  这个疑点被排掉**）、`各自耗时(ms)=33,52,73,98,118,140,161,185`、`状态=206×8`。

**读法**：不是「六个一波 + 两个一波」（HTTP/1.1 六连接上限该有的样子），也不是八个
齐平（真并行该有的样子），而是**严格排队，每 ~21ms 回一个**。所以这台电视上，对同
一主机的并发请求实际是串行完成的 —— 不管底下是 h2 还是 h1.1 单连接。**这条改了很
多东西的前提**：`bufferingGoal`、分段大小、强令牌自读 sidx 的并发上限（现在是 2），
都是按「并发有意义」定的。

**同样重要的是它证否了什么**：健康时段里 8 个并发小请求**全部 206**，没有一个被拒、
被掐、被吊住。所以「CDN 在拒绝这个客户端的成串请求」这个解释，**至少在不卡的时候
不成立**。卡住那一刻的同一组数还没取到（探测已就位，`传输形状（卡住时）`），
**在拿到它之前不要据此设计退避**：如果卡住时八个照样秒回，那毛病在我们这侧
（socket 吊着或播放器没在要），退避只会多冻二十秒。

**⟶ 2026-08-16 16:41 拿到了缺的那一半，而它把上面那条结论翻了过来。** 同一场卡顿
里，健康时和卡住时各测一次：

| 时刻 | `最后一次回来` | 各自耗时(ms) | 状态 | 形状 |
|---|---|---|---|---|
| 16:34 播放中 | 通道正忙 | 31,47,60,75,87,111,121,133 | 206×8 | 排队，每 ~15ms 一档 |
| 16:41 卡死 | **17.6s 前** | 188,204,207,210,211,216,219,236 | 206×8 | **齐平 —— 真并行** |
| 16:53 卡死 | **0.0s 前** | 255,272,274,283,305,319,339,353 | 206×8 | 排队，每 ~14ms 一档 |

**排队不是这条链路的固有属性，是竞争。** 播放器满负荷取流时，八个探测排在它的请求
后面；播放器一停止索取，同样八个请求就并行回来了。所以「这台电视上并发是串行的」
这句话**不能再拿去当配置依据** —— 它描述的是「播放器正在取流时额外的请求要排队」，
那是任何客户端都会有的现象，不是这台机器的限制。按它定下的那几个数（分段大小、强
令牌自读 sidx 的并发上限=2）依据没了，但**也不要反过来立刻放开**：没有证据说明放开
会更快，而它们现在是好用的。要动就重新测，别再靠推导。

> **第三行是同一天下午加进来的，它差点被读成反例。** 16:53 那次也是「卡住时」，形状
> 却和 16:41 相反 —— 因为**画面卡住不等于通道空闲**：那一刻 `最后一次回来=0.0s前`，
> 一个 1.5MB 的分段刚刚落地，通道忙得很（那次是 `video element error 3`，错误驱动，
> 不是看门狗的「无进展」）。**所以标签不能叫「健康时 / 卡住时」，判据是通道忙不忙，
> 读同一组日志里 `分段请求` 那行的 `最后一次回来`：十几秒前 → 通道空 → 该看到并行；
> 0 秒前 → 通道忙 → 该看到排队。** 探测行自己的 tag 只记录了「当时画面在不在动」，
> 而那**不是**决定形状的那个变量。这条差一点就以「卡住时应该并行」的形式写进文档，
> 然后被下一份样本打脸 —— 而「竞争」这个解释反倒因为提前预测对了这个差异而更硬。

**退避这条路则被彻底证否了。** 卡住那一刻：`状态=206×8`，八个并发全部成功、齐平、
两百毫秒回来 —— CDN 没有拒绝、没有掐线、没有吊住任何东西。同一时刻另外两个仪表
指向同一个方向：`分段请求 发出=209 回来=209 在飞=0 最后一次发出=17.6s前`（没有请求
在飞，我们自己不要字节了），`判别探测 xhr=206 131072B 186ms`（同一地址同一偏移，
普通 XHR 秒回）。**三个互不依赖的仪表同向，毛病在本机这一侧，立刻重建是对的做法，
退避只会白冻二十秒。**

> **同一场事故里的两次卡死，原因不同 —— 这正是判别探测存在的理由。** 456s 那次
> `判别探测 186ms`（字节又快又好，播放器却停止索取，本机侧）；换族之后 476s 那次
> `判别探测 5997ms`（同样 128KB，慢三十二倍，是 CDN 边缘没缓存过这个偏移、回源去取
> 的那种慢，网络侧）。两次症状一模一样（`卡住 N 秒无错误也无进展`、分段完整、
> `在飞=0`），**一个能同时解释两次的机制一定是假的**。avc1 那份文件 101MB 而 hvc1
> 只有 38MB，换族等于换到一份更大、更不可能被边缘缓存住的文件 —— 换族这一档因此
> **有它自己的代价**，不只是「换个解码器试试」。
>
> 顺带记一个待办级的观测：那个 `5997ms` **贴着 `connectionTimeout` 的 6000ms**。
> 这类回源请求处在「有时刚好过、有时刚好超时」的边缘，而超时后的重试还是回源、还是
> 六秒。上一轮把它从 5s 放宽到 6s 时写的是「这是妥协不是测量」——**现在有第一份测量
> 了，但只有一个样本，不足以定新值**。判据是后面还有没有 `判别探测` 落在 5–7 秒这个
> 区间；放大它的代价是真正的死连接要更久才被看门狗发现。

> **今天这三条都是「测量本身不合格」的教训，比结论值钱。**
> ① `最后一个分段请求 要 X 收到 Y` 曾用**一个全局槽**记 range、再拿下一个响应的 body
> 长度去填，视频和音频并发在飞时必然错配 —— 「要 36599B 收到 1021139B」是仪表自己
> 读错，当天却被当成「CDN 给了没人要的字节」写进了对话。现在改读响应自己的
> `content-range`，两个数出自同一个响应，没有配对可错。
> ② 形状探测第一版从**一个 t0** 起算八个完成时刻，分不清「网络在排队」和「我自己
> 发得慢」，画出的楼梯被读成 h2。现在每个请求各记发出时刻，起点和耗时分开报。
> ③ 那一版的判定规则只写了「六连接上限」和「齐平」两类，遇到排队这种没见过的形状，
> 它**不会沉默，它会撒谎** —— 印出「像多路复用」。现在多一条兜底：
> 「形状不属于已知三种，别硬套」。**一个只会在已知选项里挑的分类器，就是一个会
> 撒谎的分类器。**

> 深偏移的 range **不会**因为「深」而被拒 —— 文件末尾的 range 返回 206，字节数
> 和索引预言的一模一样，越界则返回 416。真正慢的是 CDN 边缘**从没缓存过**的
> range：一个 3.9 GB、5.6 小时的稿件，中段得回源去取，实测能取到时慢三十倍，
> 取不到时连接直接被掐 —— 从台式机发和从电视发一样。这也是清单要提供画质阶梯
> 的原因：降一档，好过等一段谁都没取过的字节。

> 任何反复驱动 AVPlay 的代码都必须给回调加世代守卫。`setListener` 注册在 avplay
> 单例上，换掉 `<object>` 元素并不会解绑，于是上一次尝试的 `onerror` 会打进当前
> 这一次。`player.js` 和 `spike/main.js` 都用世代计数器守着；没有它，一个依次
> 尝试多个源的实验会给出乱序结果，读起来像「全都失败了」。这件事发生过，而且
> 让结论完全反了。

那个 34 请求的突发没被限流，和 08-02「约 20 个请求触发冷却」**同时为真** ——
限流的阈值和键位也是当天的天气，别拿任何一天的数字当常数写进代码或者拿来
否决配置实验。

**CDN 会按「文件」歧视，同一稿件三份 1080p 各有各的命（2026-08-03 晚实测）。**
「越狱」P20 当晚：hev1 和 avc1 的 1080p 文件从桌面探是 206 但**限速到
25–50 KB/s**（512KB 分别要 10 秒和 22 秒，628kbps 的流需要 78KB/s，追不上），
对电视的令牌干脆 403；同一稿件的 **av01 文件 0.39 秒拉完，满速**。网页端在
同一秒毫无感觉 —— 不是它做了什么恢复优化，而是它默认用 AV1，压根不进坑；
我们的清单因为 SoC 软解顾虑把 AV1 整族排除，等于扔掉了唯一健康的 1080p。
应对分两步走：先给失败阶梯加了 AV1 这一档（日志认 `换 AV1 的同画质`），当晚
稍后干脆把 **av01 升为默认族**（见「清单默认走 AV1」一节，含 fnval 和长串两个
前提）。阶梯现在的形状是：**默认族原样重载 → avc1 → （默认不是 av01 时）av01
同画质 → 逐级压档**（压到当前档的下一档，不写死 —— 顶档本就是 64 的稿件写死 64 等于原样重建）；av01 自己就是默认时换族那档自动跳过。「AV1 可能是软解」已有
第一份反例数据（设备自测 1080p 全程 `丢帧=0`），`丢帧` 计数继续当裁判。这种
按文件的歧视也是按稿件来的：P18/P19 的 hev1 一整晚都好好的。

**歧视也会整档整稿件地来：登录才有的那几档全灭，而免登录的低档满速（2026-08-09
22:30 实测）。** `BV1hCQsBDEAL`（蜡笔小新 恐怖系列）当晚 **720P 和 1080P 的每一份
文件、在 cosov 和 akam 两台主机上、hev1/avc1/av01 三个族无一幸免，全部 403**，而
**同一台 akam 主机上，这个稿件的 480P（`-1-30032`）和 360P（`-1-30011`）各取
131072B、206、满速**。判别做全了，几条容易上当的解释各自被排掉：

- **不是限流。** 一分钟后的下一个视频 1080p hvc1、`playing=1696ms`、零错误。
- **不是地址过期。** `deadline` 当时还剩 115 分钟。
- **不是当晚换成 access_key 的锅**（那天刚把会话从失效的 `Cookie` 头改过来，是个
  新变量，必须排）。匿名和登录**对每个视频**都只在 720P 以上设门槛 —— 被拒的和
  正常的两个稿件匿名都只给 `[32,16]`，不是这个稿件被针对；而同一个登录账号、同样
  带 `mid=` 的地址在下一个视频上完全正常。
- **`video element error 3` 是它的下游，不是解码问题。** init 段「完整」送达却解不
  了 —— 403 的 HTML 错误页被当成分段喂进了解码器。`最后一个分段请求 … （完整）`
  这行就是用来分开「半截数据」和「根本不是媒体数据」的。

**这是分钟级的天气，不是这个稿件的属性。** 十分钟后（22:40）同一个稿件、同一个
账号重播：cosov 仍然拒 `-1-30077`/`-1-30280`，但**镜像轮转到 akam 之后 1080P 直接
活了**（`判别探测 xhr=206 … 档=80 hev1`，随后 `恢复播放 … 1920x1078`），压档那几档
一步都没轮到。所以别把 `BV1hCQsBDEAL` 记成「有毒的稿件」—— 22:30 那一刻它在两台
主机上确实全灭，22:40 它好端端的。

**代价落在我们自己身上：那天梯子压到 720P 就没有下一级了**（守卫是「没压过才压」，
第一次压完就把自己的门关上），于是在 480P 和 360P 健康地摆着的情况下打出「所有路
都试过，有声退出」。现在逐级下降，停止条件是「下面没有档位了」。**注意这一档到
2026-08-09 为止只有离线验证**（用真实档位跑过步序和终止性：`80→64→32→16→交给上
层`，单档稿件不压），**设备上还没有一次真正触发过** —— 22:40 那次重播被镜像轮转
提前救走了。看到 `从 qn64 再压到 qn32` 这行才算它在野外跑过。**已知限制**：
`triedAv01` 不会随降档重置，所以换族那一档只在最高的那一级试过一次 —— 降档之后是
另一批文件，理论上值得再试，但每一级都试会把黑屏时间拉长，暂时按不试处理。

**⚠️ 上面这套「压档 / 换族 / 镜像轮转」是给「按文件的天气」擦屁股的；真正让这类
稿件在电视上放不了的根因，2026-08-11 查明并根治了，另有专文。** 一句话：CDN 按
playurl 请求的 `platform` 决定流令牌强度，web 端点（`platform=pc`，我们一直走的）
铸的令牌被严格节点 403，**app 端点（`app.bilibili.com/x/playurl`，`platform=android`）
铸的令牌被接受**——这就是「同一稿件同一秒手机能放、电视不能」。根治是撞 403 时改用
app 端点铸强令牌、自读文件头补上 app 端点不给的 SegmentBase（`api.js` 的
`playurlDashStrong`、`player.js` 的 `offerStrongToken`、`app.js` 错误处理最前那段）。
**完整排查过程、判别实验链、两次把「天气」当诊断的错判与纠正、已知边界，见
[`docs/播放流令牌-app端点根治.md`](docs/播放流令牌-app端点根治.md)。** 读那份之前先记住
它的结论：`platform` 是变量，不是认证方式、不是参数、不是天气。

**没登录就没有强令牌**（app 端点不带 access_key 铸的就是被拒的那种，见那份专文）。2026-10-23/24 两台没登录的电视（Tizen 4.0、6.0）
大多数视频 web 令牌 403、DASH 全灭，屏幕上一直是「可能是临时限流，过几分钟再试」。没账号时最后那句改成「先去「我的」扫码登录再试」。

**而这条根治在门口漏了五天：它要 `aid`，而起不来的视频恰恰没有 `aid`（2026-08-16
发现并修好，当天设备验证）。** 守卫写的是 `playing.detail.aid`，`aid` 有两个来源，
对一个起不来的视频**两个都不在**：

- **首页推荐那个接口只给 `id`，不给 `aid`**（`index/top/feed/rcmd`；08-16 对四个
  接口逐个实测，热门 / 排行 / 相关都给 `aid` 且都不带自己的 `id`，只有推荐是例外），
  而 `normalise()` 读的是 `v.aid` —— 于是首页进去的每张卡片 `aid` 都是 undefined。
- **补齐 `aid` 的 `view()` 调用被刻意推迟到画面起来之后**（`loadMetaForPlaying`，
  为的是不和播放器抢这台机器本来就不快的链路）。

合起来就是：**为「播不起来的视频」造的逃生路，只有「已经播起来的视频」走得进去。**
08-16 16:16 的日志把这件事摆成了对照实验 —— 同一分钟、同一批 403（akam 和 cosov
一起拒）、同一个交接信号 `web 令牌 403，交给 app 端点强令牌`，四个视频两种结局：

| 视频 | 起过画面吗 | 结局 |
|---|---|---|
| BV1fQgX6CE9N | ✅ 播了 43 秒，`view()` 早已填好 aid | `直奔 app 端点强令牌，从 0:39 重建` → **活** |
| BV1v2gY6jEiT / BV12m396FE9m / BV1adKh6oEoi | ❌ | `DASH 全灭` → 渐进式 → `所有路都试过，有声退出` |

修法两层，缺一不可：`api.js` 的 `normalise()` 改成 `v.aid || v.id || 0`（补上推荐
入口，零成本），`app.js` 的守卫不再要求 aid 在手 —— 缺了就用 bvid 换一次
（`withAid()`，日志认 `手里没有 aid（这个入口的卡片不带），先用 bvid 换一次`），
一次往返只在 403 这条路上付。**`mergeHistory()` 也补了一行**：`aid` 属于稿件而不
属于分 P，所以它跨 P 传递，不能像 `cid`/`page` 那样关在 `samePart` 里 —— 本地续播
记录从不存 `aid`（`resume.js` 里一个都没有）而服务端历史总是有，本地卡片赢 recency
时 aid 就在合并里丢了，「继续观看」最上面那几张正是这种。
