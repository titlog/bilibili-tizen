# 账号与登录

> 从 CLAUDE.md 原样搬出（2026-10-20 精简时）。这里是排查经过、现象和测量数据；CLAUDE.md 里只留现在成立的结论。
> 文中「见『某某』一节」指原 CLAUDE.md 的小节，现在分在 docs/ 下的各个文件里，按标题搜即可。

## 一台电视，好几个人

这台电视是共用的，所以 `accounts.js` 持有的是一个账号列表而不是单个会话，
`Accounts.scope()` 给每个人各自的存储命名空间。观看记录按账号隔离；
`settings.js` 不隔离，因为首选画质属于这台电视，不属于某个观众。

**cookie jar 正是采用 TV 登录路径的原因。** 多账号需要这段代码能存下来、能重放
的凭证。网页流程的 ticket 跳转把凭证放进了一个不可读、不可写、而且全局的地方
—— 一次只能装一个账号，而且没有任何办法把上一个放回去。`passport-tv-login` 以
JSON 返回 `SESSDATA`、`bili_jct` 和 refresh token，这样拿到的账号可以随时切换、
长期有效。代价是它的请求要用官方 TV 客户端的 appkey 签名，也就是对 bilibili 表现
成那个客户端。**这是一个刻意的决定，不是疏忽。**

网页流程保留为兜底，而且回落发生在**任何二维码到达屏幕之前** —— 在别人已经举着
手机对准的时候把码换掉，比失败更糟。走了兜底路径的账号，一旦 jar 易主就会被
`Accounts.needsRelogin` 标记，界面会要求重新扫码，而不是悄悄用别人的名字端上一个
未登录的信息流。

**`withCredentials` 不再是「只要登录了就设」。** 它原本是对「固件可能拒绝
`Cookie` 头」的两头下注。但这台电视上有多个账号之后，那个下注变成了泄漏：jar 是
全局的，这个标志会把最后一个走网页兜底登录的人，挂到别人名下发出的请求上。
`api.js` 现在只在活动账号确实是 jar 的主人时才设它。

**⚠️ 这个固件不允许 widget 设置 `Cookie` 头（2026-08-09 实测推翻）。被选中的账号
靠 `access_key` 走 query 到达服务器。**

这一节此前写着「这个固件确实允许 widget 设置 `Cookie` 头 —— 2026-08-02 在设备上
实测，而整个账号设计压在这条上」。**那次实测没有区分能力，而这条错误结论在文档里
待了七天。** 当时电视上只有一个账号，而在只有一个账号的时候，我们设的 `Cookie` 头
和引擎自己那个全局 cookie jar 必然指向同一个人 —— 不管请求实际带的是哪一个，
服务器都答同一个名字，`服务器认得 X` 恒为真。**它证明的是「有人到达了服务器」，
被当成了「被选中的那个人到达了服务器」。** 判别实验要到第二个账号出现才做得成。

08-09 晚上第二个账号出现了，症状是第二个人扫码登录之后，显示的还是第一个人的信息。两个
方向各测一次：

| 谁发的 | 内容 | 结果 |
|---|---|---|
| 电视 | 两秒新的 TV 登录会话，`setRequestHeader("Cookie", …)` | `isLogin=false` |
| 电视 | 什么都不带（对照） | `isLogin=false` |
| 开发机 | **一模一样的头**，含 `cookieHeader()` 自造的 `buvid3` | `isLogin=true` |
| 开发机 | 什么都不带（对照） | `isLogin=false` |

凭证是好的、头的内容也是好的（`buvid3` 一并洗清），是电视没把这个头发出去 ——
`Cookie` 是 forbidden header name，Chromium 120 对它的 `setRequestHeader` 静默忽略，
widget 的 `<access>` 策略并不豁免。**所以这个应用发出的每一个登录态请求，要么是
匿名的，要么穿着 jar 里碰巧那个人的衣服**；一个账号时 jar 里碰巧就是对的人，于是
一切看起来正常。这也解释了存档为什么会被改写成「三份不同的凭证、同一个 mid、同一
个名字」：身份不是登录给的，是事后 `nav()` 问出来、再由 `Accounts.describe()` 盖到
活动行上的，而 `nav()` 答的是 jar 里那个人。

**现在承载会话的是 `access_key`，`api.js` 的 `withSession()` 把它签名后拼进 query。**
query 参数没人能剥掉，没有「全局一个坑位」可供互相驱逐，切换期间已经在飞的请求也
仍然带着它被发出时那个账号。覆盖面 08-09 逐个实测过：`nav`、`rcmd`、动态、
`history`、`history/cursor`、`player/v2`、`playurl`（12 个表示，与 cookie 会话基准
一致，未登录只有 6 个）、app 版 feed / myinfo。**只发给 `api.bilibili.com`** ——
token 是凭证，搜索建议那台主机没有理由拿到它。网页兜底进来的账号没有 access_key，
它们仍然只能靠 jar（`jarIsOurs()`），这条没变。

`Auth.cookieHeader()` 仍然照设，成本为零、指的是同一个账号，将来哪个固件肯认它是
它的自由。AVPlay 的 `setStreamingProperty("COOKIE", …)` 是另一套栈，不受这条影响。

每次启动上报的那两行现在长这样，而且**探测三条路各问一遍**，固件哪天变了会自己
喊出来，不必再靠断言：

```
account: 4 个账号，当前 route=access_key，服务器认得 <用户名>
whoami: 启动 活动=a4 access_key=有 header=有 1ed07418 jar主=无 withCred=否 | a1 mid=… 凭证=…
whoami: 启动 常规                        → isLogin=true mid=<mid> uname=<用户名>
whoami: 启动 只有 Cookie 头·不带 access_key → isLogin=false
whoami: 启动 裸请求·什么都不带              → isLogin=false
```

判据是 **mid 对不对得上**，不是「认不认得出人」。`--selftest` 里那一步同样改成比
mid：它以前问的是「服务器认得某个人吗」，于是这个 bug 从它眼皮底下过了七天。
`Accounts.describe()` 现在也拒绝把一个不同的 mid 写进已有身份的行 —— nav 答的人跟
这一行不是同一个人，说明的是「这次请求没带上这个账号的会话」，不是「这个账号改名
了」。日志认 `服务器答的是 mid=… 而活动账号 … 是 mid=… —— 这次请求没带上这个账号
的会话，身份不采信`。

**账号层的 bug 是静默的，所以在设备之外测。** 记录记到别人头上、上一个账号的
cookie 顺风搭车、一个账号声称已登录但背后什么都没有 —— 这些都不抛异常、都不会
到达收集器，表现出来全都是「bilibili 有点怪」。`tools/accounts-verify.mjs` 用假
`localStorage` 和假 XHR 驱动整层，`tools/md5-verify.mjs` 把签名摘要对着 node 的
实现核对，任何一个失败 `deploy.sh` 都拒绝发布。

## 登录（原「进展与缺口」一节里的记录）

**登录 —— 已完成**，扫码，支持这台电视上的任意多人。值得留档的发现：

- *不需要 WBI 签名。* `search/all/v2`、`popular`、`ranking`、`view`、`playurl`
  都能无签名应答。只有 `search/type` 要签名，而 `search/all/v2` 覆盖了同样的
  场景。**⟶ `view` 这一条 2026-09-07 反转了一半**：`/x/web-interface/view` 从这个
  网络答 **HTTP 412**（风控 HTML 页，不是 JSON）——电视 UA、桌面 UA、带 Referer、带
  `buvid3`、按 aid 问，全 412；同一台主机上 `archive/related` 和 `player/pagelist`
  照常 200，而它的 wbi 孪生 `/x/web-interface/wbi/view` **不签名**就答 200、载荷
  一样。分 P 列表、简介和强令牌要的 `aid` 全出自这一个调用，所以 412 的表现是
  「按下键面板里没有分 P」加「403 那条路换不到 aid」，而且**两处都静默**——
  `loadMetaForPlaying` 的失败回调曾是 `function () {}`。现在 `API.view` 失败（非
  -404）就退到 wbi/view，哪条答上了记在 `meta:` 那行；面板把「还在加载」「加载
  失败（原因）」和「本来就一 P」分开写。电视自己带 access_key 的请求是否也吃 412——
  **2026-09-16 在设备上答了：带不带都 412**（各两发，0/2 对 0/2），wbi 孪生端点是唯一解。
  **2026-09-28 起挨过一次 412 就 30 分钟内先问 wbi/view**（它被闸再退回 view）：当天 14 个
  视频 14 次 412，每次都是往正在拒绝我们的那道 IP 闸上白撞一发。日志认 `meta:` 行尾
  「（view 近来被闸，先问它）」。
- *网页轮询的响应不携带凭证。* 它返回一个跨域地址，query 里只有
  `ticket, gourl, first_domain` —— 会话是那一跳的 `Set-Cookie`，XHR 读不到。
  兜底路径因此用 `withCredentials` 取那个地址，让引擎自己的 jar 收下 ——
  这意味着**那条路径永远看不到 SESSDATA**。
- *TV 登录路径携带凭证*，这就是它存在的理由。
- 二维码由 `qr.js` 在设备上编码，而不是从图片服务取：载荷是一次性登录令牌，
  任何能读到它的人都能以用户身份完成登录。`tools/qr-verify.mjs` 会把编码器过
  一遍真实解码器 —— **改动那里之后跑它。**

## 视频互动的写接口

**视频互动按登录路径分流（PR #2，2026-10-18 移植）。** 点赞、投币与逐个收藏夹的加入/移出
优先用 TV 登录返回的 `access_token` 走 APP 接口（`Auth.signTv()` 签名）；只有属于当前账号的
浏览器 Cookie 和 `bili_jct` 同时可用时才走网页写入接口。网页兜底账号通常拿不到 `bili_jct`，
界面必须明确说明无法提交，绝不能先改本地状态再假装服务器接受了。`tools/compat-api-verify.mjs` 用假传输层核对每条写请求的去向和参数，
以及没有凭证时一个写请求都不发。**2026-10-18 在这台上实测过一次**（TV 登录账号，自测里临时加的步骤，
没有提交）：点赞→`has/like` 答 true→取消→答 false；加入「默认收藏夹」→移出→`list-all?rid=` 答不在；
都回到原状。投币只读过状态（「已投 0 / 2 枚」），**没有真投过**——它撤不回来。评论的写接口
（`x/v2/reply/action`）从电视直连是 403，所以评论只读。

### 老引擎的写请求被网关按 Origin 拒（2026-10-25）

一台 Tizen 4.0（Chromium 56）的电视，TV 扫码登录、`access_key` 在，读什么都正常（`whoami` 的 mid 对得上），
**写什么都不行**：观看进度上报和关注连着几天 `HTTP 403`，`access_key`、`csrf` 两种凭证都是。

这个 403 不是接口回的（接口的拒绝是 HTTP 200 加 JSON 错误码），是 bilibili 网关回的一页 HTML。
从开发机各发一次 `history/report`，只改 `Origin` 头：

| Origin | 结果 |
|---|---|
| 不发 | 200，JSON `-400` |
| `https://www.bilibili.com` / `api.` / `app.` / `space.bilibili.com` | 200，JSON |
| `file://`、`null`、`app://…` | **403 网页** |

GET 也一样查（`nav` 带 `Origin: file://` 也是 403 网页），但浏览器只在 POST 上带 Origin，所以那台电视读得到、写不了。
**Chromium 56 的 widget 每个 POST 都带上自己的来源**，这台 CU7090（Chromium 120）一个都不带，所以这边从来没撞上过。

查不查 Origin 是按路径分的：

- 查：`x/v2/history/report`、`x/relation/modify`、`x/relation/batch/modify`、`x/relation/tags/addUsers`，
  换成 `api.biliapi.net` / `api.biliapi.com` 也一样。
- 不查：`app.bilibili.com/x/v2/view/like` 和 `coin/add`、`medialist/gateway/coll/resource/deal`（点赞、投币、收藏走的都是这些）。

关注的接口全在 `x/relation/` 下面，换接口绕不过去。绕过去的办法是抖音那边的：widget 能脚本化跨域 iframe。
在 `api.bilibili.com/robots.txt`（30 字节纯文本）上开一个隐藏的框，用**框里的 `fetch`** 发 POST，请求就是同源的，
带的是 `Origin: https://api.bilibili.com`，网关放行。`api.js` 的 `postForm` 收到网关那页 403 之后，用同样的字节从框里再发一次，
这次运行之后的 api.bilibili.com 写请求都直接走框。只有 api.bilibili.com 的写请求走这条路；JSON 的 403 也不算。

- 用 `fetch` 不用框里的 XHR：同源的 XHR 不管 `withCredentials` 怎么设都会带上框里的 cookie，而 jar 可能是另一个账号的。
  请求体里有 `access_key` 就 `credentials: "omit"`，只有网页登录那条 csrf 路才带 cookie。
- **Chromium 56 让不让脚本进跨域框，还没见过**（抖音的框在 Tizen 6.5、9.0 上见过）。日志里那一行会说：
  `api: 从框里发过去了（…ms，code 0）`，或者 `api: 框用不了：这台电视不让脚本进跨域框（SecurityError），写操作只能失败`。
- `--selftest` 在这台电视上强制走一次框（播放中的进度上报，真写），`tools/gated-verify.mjs` 用假框核对去向和字节。
- 评论的写接口从这台电视也是 403（见上），是不是同一道闸还没查过。

## Token 续期

**Token 续期没有实现。** TV 登录的令牌带着 `expires_in` 和 `refresh_token`，
端点是 `passport-tv-login/oauth2/refresh_token` —— 但确切的参数命名没有对着服务器
验证过，而把一个未经验证的猜测塞进唯一保管全家凭证的那条路径，正是这个项目吃过
亏的做法。在验证之前，过期的账号表现为「我的」显示「会话已失效」，需要重新扫码。
`app.js` 里的 `refreshActiveProfile()` **刻意不**根据 `isLogin:false` 采取行动：
那个回答在「令牌过期」和「`Cookie` 头被丢弃」之间是二义的，凭它把每个存下来的
账号标记为失效，等于拿猜测销毁凭证。
