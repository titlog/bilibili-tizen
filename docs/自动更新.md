# 自动更新

> 从 CLAUDE.md 原样搬出（2026-10-20 精简时）。这里是排查经过、现象和测量数据；CLAUDE.md 里只留现在成立的结论。
> 文中「见『某某』一节」指原 CLAUDE.md 的小节，现在分在 docs/ 下的各个文件里，按标题搜即可。

## 最初的可行性探测（2026-08-03）

**这个 widget 可以自己更新自己 —— 五条路全通，2026-08-03 设备实测。**
分发只能靠侧载（三星商店不收第三方客户端，见「开源与分发」一节），而侧载要一台
同网段的电脑、Tizen 工具链和一张三星分发证书。让观众为每个修复重做一遍，等于让
他们别用。`app/js/updater.js` 的探测回答了这件事可不可行：

| 能力 | 结果 |
|---|---|
| `new Function`（CSP `unsafe-eval`） | 可用 |
| `blob:` 脚本注入 | 可用 |
| 远程 `https` script 标签 | 可用，95ms |
| `wgt-private` 写入→读回 | 可用，回环一致 |
| jsdelivr / raw.githubusercontent / codeload | 206 / 206 / 200，55–335ms |

三条执行路径任选其一即可跑新代码。**关键是第四条**：能落盘就意味着更新可以存下来
下次直接用，而不是像社区版 Twitch 那样每次启动都必须联网 —— 断网时电视照样开得起来。
jsdelivr 最快（55ms），三个托管都可达。**⟶ 2026-10-18 做成了，见「自动更新」一节；`updater.js` 这个探测删了。**

> **⚠️ 这五条全通，只因为 `config.xml` 里没有 `<tizen:allow-navigation>` 和任何 `<tizen:content-security-policy*>`。**
> 三者出现任何一个，应用就从「WARP 模式」（只由 `<access>` 管，没有 CSP）切到「CSP 模式」，没写 CSP 时套默认策略
> `default-src *; script-src 'self'; style-src 'self'; object-src 'none';` —— `new Function`、`blob:` 脚本、远程脚本、
> `data:` 图片、HTML 里的内联 `style` 属性**全部被拦，而且静默**（不抛异常，只有 `securitypolicyviolation` 事件说得出）。
> 官方 Web Runtime 文档里写着，2026-09-30 设备实测：同一个探测 widget 只改一个变量装了 4 个变体，有
> `allow-navigation` 的两个全拦、没有的两个全放，权限多少无关。**往 config.xml 里加这三个元素之前，先想想更新器。**
>
> **⟶ 2026-10-20 解法已经验证过**：douyin-tizen 是 CSP 模式（签名桥要 `allow-navigation`），它的自动更新照搬这一套，只在
> `tizen:content-security-policy` 的 `script-src`、`style-src` 各加 `blob:`，样式改成 `blob:` 的 `<link>`（这边用的内联 `<style>`
> 在 CSP 模式下被拦）。电视上实测下载 → 下次打开跑新代码 → 再开还是新代码全通；对照（去掉 `blob:`）起不来、下次退回安装包。
> 详见那边 CLAUDE.md「自动更新」。

> 这个探测本身踩了两个坑，都值得记。**一是 `FileStream` 没有 `readText()`**，
> 只有 `read(charCount)`；写错的那次抛了未捕获的 TypeError，把探测拦腰打断，而
> **唯一说出这件事的是 `window.onerror`**。二是最初写成
> `try { Updater.probe(); } catch (e) {}` —— 静默吞掉异常，于是「定时器没响」和
> 「探测崩了」在日志里长得一模一样。现在到点先无条件报一行再开始探测，正是这一行
> 让「电视睡着了」这个诊断能够成立：同步的 `engine:` 发得出去，而 1.2 秒和 6 秒的
> 定时器一个都不响。

## 自动更新（2026-10-18）

用户要求做（探测 08-03 就全通了，一直没做成产品）。**信任根是签名，传输不可信**：

- **钥匙**：ECDSA P-256 + SHA-256。公钥（SPKI）写在 `app/js/boot.js` 的 `PUBKEY`，指纹 `dba4:4772:0818:d6d8:7370:21ac:3915:5b49`。
  私钥在这台 Mac 的 `~/.bilibili-tizen-update-key.pem`（600，aes-256 加密），口令在 `~/.bilibili-tizen-update-password`（600），
  **都在仓库外**。**丢了**：以后发更新就得让所有人重装一个换了公钥的包。**泄露了**：谁都能往每一台装着它的电视推代码 —— 而这个
  应用拿着全家人的 bilibili 令牌。签名格式是 IEEE P1363（r||s），WebCrypto 要这种；node 签要 `dsaEncoding: 'ieee-p1363'`。
- **更新包**：`tools/update-release.mjs` 从 `git archive HEAD` 取（`app/` 有未提交改动就拒绝），打成一个 JSON：body 的静态 DOM、
  CSS、脚本和它们的顺序；`update/manifest.json` 写版本、`shell`、sha256、大小，并对 manifest 正文签名。**永远不带**：`config.js`
  （deploy.sh 每次改写，里面是上报地址和 SELFTEST）、`boot.js`（信任根）、`vendor/`（Shaka，player.js 从包里注入）。约 780KB。
- **从哪取**：manifest 先问 `raw.githubusercontent.com/titlog/bilibili-tizen/master/update/manifest.json`，不行再问 jsDelivr 的
  `@master`；bundle 按 tag 取（jsDelivr `@v<版本>`，不可变、缓存友好），不行退 raw。只有开发构建（`REPORT_TO` 非空）能用
  `bili.update.source` 把检查指到别处 —— 发布包只能查仓库。
- **连不上 GitHub 的网络（2026-10-22 起，1.3.6）**：上面两个在有的网络里都靠不住（raw 解析不了，jsDelivr 时通时断），
  所以 manifest 和 bundle 的第一个地址都改成自己的域名 —— 诊断日志那个 Worker 的 `GET /v1/update/<应用>/manifest.json`
  （转 master 上的，缓存 5 分钟）和 `…/bundle-<版本>.json`（转 `v<版本>` 这个 tag 上的，缓存 30 天），三个应用共用；
  GitHub、jsDelivr 退成后两个。**中转不需要被信任**：manifest 有签名、里面写着 bundle 的 sha256，改一个字节电视都不收。
  `不用下载：…（清单来自 <主机>）` 和 `已下载 …来自 <主机>` 说明这台电视走的哪条。**先有鸡的问题**：来源列表在 `update.js` 里、
  随更新下发，一台从来连不上 GitHub 和 jsDelivr 的电视收不到这次更新，只能重装 1.3.6 以后的包。
  发 1.3.6 那天量的：raw 自己缓存约 5 分钟，中转在那之前取到的旧清单再留 5 分钟，而且是每个边缘节点各留各的 ——
  发版后十分钟内同一个地址会时新时旧（只是晚一轮检查，不会错）。jsDelivr 的 `purge` 发版后**等 raw 更新了再按一次**：
  早按了它会去取 raw 的旧版本，连按几次就被限流 45 分钟（`throttled`）。
- **启动时（boot.js）**：index.html 里只剩 `config.js` 和 `boot.js` 两个脚本标签，**以后新加脚本要加进 boot.js 的 `SCRIPTS`，
  不是 index.html**（`tools/lint.mjs` 从那里读顺序）。本地有已验过、版本**高于安装包**、`shell` 不超过这台的、没标坏过的更新包就用它：
  换掉 body 的静态 DOM 和 CSS，**在页面解析期间**用 `document.write` 写 `<script src="blob:…">` —— app.js 靠 `window.onload` 启动，
  解析结束后再插脚本就错过 onload，这是硬约束。**启动时不再验签**：更新包从这个应用自己的 localStorage 来，能写那里的人早就能跑代码了；
  下载时验过才存。手动装了更新的安装包，旧的下载自动作废。
- **坏了能退回**：用更新包启动前记 `booting`；app.js 在 onload 跑完、两秒内没有一个 js 错误、屏幕上有东西时调 `Boot.ok()` 清掉。
  **不等首页 feed** —— 断网时首页出不来，那不是代码坏了。下次启动看到 `booting` 还挂着 → 那一版标坏、用安装包，以后也不再下载它。
  **⟶ 2026-11-14 起（boot.js 1.5.1）分两种「没走到」**：`booting` 记成 `版本#次数`。这次启动**自己看见了失败**——启动期间出了 js 错误
  （boot.js 自己挂的 `error` 监听，app.js 的 `window.onerror` 管不到它前面的脚本、也管不到解析不了的 app.js），或者 app.js 两秒时
  发现屏幕是空的、调了 `Boot.fail()`——记成 `版本#!`，下次照旧当场标坏。**什么都没说就没了的**（没出错、没调 `Boot.ok()`）
  再给一次，日志 `update: …上次用 X 启动没走到首页就没了（没出错，多半是被打断），再试一次`，不算出事；连着两次才标坏，
  note 写 `（连着 2 次）` 或 `（启动时出了错）`。来由：11-07 马来西亚一台 Tizen 5.0、11-14 台湾一台 Tizen 9.0，都是同一版 1.4.14
  正常启动过很多次之后，隔了十二小时的一次启动**一行日志也没留下**（日志 15 秒或页面隐藏时才落盘，所以那次几秒内就没了、也没触发
  页面隐藏），下一次就把 1.4.14 标坏、删掉，各自退回安装包 1.4.12、1.3.2，直到下一版发出来。**这条在 boot.js 里，不随更新包下发**：
  只有装了 1.5.1 以后安装包的电视才是这样，之前装的还是一次就标坏（它们的 boot.js 认的是光版本号；新 boot.js 把光版本号当一次）。
  `update-verify` 卡着每种状态，`update-e2e` 里启动就抛错的 9.1.0 照旧下一次就退回。
- **检查**（update.js，本身随更新下发）：**每次开机** 60 秒后、没在播放时查一次（不看上次什么时候查的），开着就每 6 小时；
  从后台回来、离上次检查超过一小时，再一分钟后查一次（`Update.wake()`，app.js 的 `wokeUp` 叫它）。10-22 以前开机也要等满离上次
  6 小时：那天一小时发一版，#5 那台每版装好就查过一次，之后再怎么开都不查，回复里写的「用一会儿，下次打开就是新的」对他不成立，
  他每版都用 Apps2Samsung 重装（日志里「装的」= `appInfo.version`，自动更新改不了它）。**没成的检查 15 分钟后再查、连着失败每次翻倍、封顶 6 小时**
  （`K_LAST` 里记 `fails`，日志 `…；15 分钟后再查（连着第 1 次没成）`；「不用下载」不算失败）；manifest 签名、版本、shell、没标坏 → 下载、对 sha256 →
  存 localStorage（存不下报一行跳过）→ 下次打开生效。日志 `update:` 每种结论分开说（签名不对 / sha256 不对 / 版本不更高 / 存不下）。
  设置页「自动更新：开 / 关」（默认开）和「现在检查」，下面一行写装的是哪版、正在跑哪版、下好了哪版、上次检查的结果。
- **规则**：改了 boot.js 对更新包的约定，`SHELL` 加一（旧电视会跳过那一版，要重装）。`config.xml` 的版本号和 boot.js 的
  `PACKAGED_FALLBACK` 要一致（update-verify 卡着）。没有 `crypto.subtle` / TextEncoder 的引擎（可能是很老的电视）不更新，只在启动那行说。
- **发布一版**：① 改 config.xml 版本号和 boot.js 的 `PACKAGED_FALLBACK`，提交；② `node tools/update-release.mjs`；③
  `git add update && git commit && git tag v<版本> && git push origin master v<版本>`（tag 要一起推：manifest 从 master 取，bundle 从 tag 取）；
  ④ 可选 `zsh tools/release.sh` 出同版本的 wgt。**已经装着的电视只有装了带这套代码的版本之后才会自己更新** —— 第一次还得侧载。
- **测过的**：`update-verify` 36 条；`update-e2e` 在桌面浏览器里：发 9.0.0 → 下载 → 重新打开跑新代码（新脚本在 load 之前跑完，onload
  照常启动，body 和 CSS 换了）；一个启动就抛错的 9.1.0 → 第二次启动退回安装包、之后不再下载；篡改的 bundle、篡改的 manifest、
  更旧的版本各自被拒。
- **电视上（10-18，发 1.2.0 时）**：装一个标成 1.1.0 的开发构建，开机一分钟后 `已下载 1.2.0，下次打开生效（794KB 来自 cdn.jsdelivr.net，792ms）`
  （bundle 按顺序先问 jsDelivr 的 tag；验签、sha256、localStorage 存 794KB 都过）；`sdb shell 0 kill BiliTvApp0` 再
  `tizen run` → `这次跑的是更新 1.2.0（安装包 1.1.0）`，再杀再开还是 1.2.0（`Boot.ok()` 清掉了 booting）；最后装正式的 1.2.0 →
  `下载过的 1.2.0 不比安装包 1.2.0 新，删掉了`。测的时候踩到：**1.2.0 的检查失败了也要等满 6 小时才再查**（15:18 那次 manifest 还没推上去、
  404，之后开机都不查，只好清 `bili.update.last`）。同一天改成失败后 15 分钟起翻倍（见上），随 1.2.1 发出（10-18 19:40）—— 装着 1.2.0 的电视按旧规则最多 6 小时查到它，之后才是新规则。
