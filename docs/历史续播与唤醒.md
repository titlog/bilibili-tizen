# 观看记录、续播与挂起唤醒

> 从 CLAUDE.md 原样搬出（2026-10-20 精简时）。这里是排查经过、现象和测量数据；CLAUDE.md 里只留现在成立的结论。
> 文中「见『某某』一节」指原 CLAUDE.md 的小节，现在分在 docs/ 下的各个文件里，按标题搜即可。

## 观看记录、上报、继续观看、下架的稿件、重开电视

**观看记录两边都有，「我的」里合成一条时间倒序的列表。** `resume.js` 维护本地
列表，按账号隔离；`API.history()` 取 bilibili 账号上的（手机 / 网页端）；
`mergeHistory()` 按 bvid 合并、按时间排序。曾经分成两段，结果是本机记录满 24 张
卡时手机那段被压到六排以下、根本看不见，被当成没同步报了上来 —— 而日志里
24 条一条不少地到了。

**电视上的播放也会上报回 bilibili**（`API.report()` → `/x/v2/history/report`）。
节奏是**每 30 秒一次**，外加停止播放时一次、播完一次（`progress=-1`）。官方网页
播放器是 15 秒；这里故意慢一倍，因为这是真人的账号，快一倍只换来「新鲜到 15 秒」
而不是 30 秒。位置进入片尾 30 秒以内就报 `-1`，和 `Resume` 画的是同一条线 ——
否则两边会对同一个视频给出相反的说法。

**这个接口只认 `access_key`，不认 `csrf`。** 同一份 body（aid/cid/progress/csrf）
在登录着的 Chrome 里返回 `code 0`，从电视上发就是 `-400 请求错误`；加不加
`Referer` 都一样 —— 浏览器去掉 `Referer` 照样通过，所以差的不是它，是电视发不出
网站认得的 `Origin`，而 `setRequestHeader` 伪造不了。TV 登录同时给了
`access_token`，放进 body 里用登录那套 appkey 签名（`Auth.signTv()`），不依赖任何
请求头。日志里 `上报成功，走的是 access_key` 那行记的就是这件事。网页扫码兜底
进来的账号两样都没有，会静默地不上报，所以 `reportProgress()` 在日志里说一次。

本地列表没有因此变成冗余：它是即时的（进度条随卡片一起出现，不用等一个请求）、
它知道最后 30 秒（上报间隔不知道）、它对网页扫码进来的账号仍然有效、请求失败时
它还在。

**首页最上面是「继续观看」**（`resumeRowItems()`，四条，正好一行），来自同一份合并
历史，去掉已看完的。打开电视第一眼、光标已经落在没看完的那个上 —— 之前要按到「我的」
再等两个请求。服务端历史在启动时就取（`fetchServerHistory()`，60 秒内复用），和首页
feed 并行，所以那一行是首屏的一部分而不是事后插进来的；万一晚到，只在**观众还没动过
光标**时才补插 —— 一行内容从眼皮底下把整页顶下去，比没有这一行更糟。「我的」也改成
并行取，不再是 nav 回来了才发历史请求。

注意 `#feed-grid` 这个 id：续播那一行的卡片同样带 `data-i`，指向的却是另一个数组。
追加下一页、记住返回位置、恢复焦点，**三处都必须按 `#feed-grid` 限定**，否则会打开
毫不相干的视频。

**被删掉的稿件不再挂在「继续观看」里（2026-08-12）。** 搬运稿被下架是常态，而卡片
比流活得久：`BV1GAu163EXE`（瑞克和莫蒂 第九季）当晚两条 playurl 和 `view` 全答
`-404 啥都木有`，同一部剧在别的 bvid 下好好的。现在 `-404` 会 `Resume.markDead(bvid)`，
`resumeRowItems()` 按这份名单过滤。几个刻意的决定：

- **过滤放在合并之后**，因为死卡片有两条来路（本机记录 + 账号的服务端历史），只删一
  条另一条照样把它端上来 —— 这正是「静默的空操作」的形状。
- **只从「继续观看」拿掉，记录不删。**「我的」照旧列它：它确实被看过，下架不改变这
  件事；而且 `resume.js` 为「删整条记录」已经付过两次学费（`record()` 和后来的
  `finished()`，都曾让看过的视频从「我的」消失）。
- **名单是设备级的**（`bili.dead.v1`，不走 `Accounts.scope()`）：下架是稿件的属性，
  不是观众的属性，一个人撞上了就不必让另一个人再撞一次。
- **七天过期，而且播成功就清掉**（`markAlive`）：`-404` 多数是下架，但「审核中」答的
  一模一样，隔天就回来了 —— 一个不会过期的标记会拿一条已经不成立的证据把它永久藏起来。
- **标记之前先做判别实验**：playurl 问的是**某一 P**，`-404` 可能是稿件没了，也可能
  是这台电视记着的 cid 过期了（分 P 被重传），两者长得一模一样而正确答案相反。所以
  只有 `view` 也答 `-404`（或 `62002 稿件不可见`，2026-09-28 补：BV1pPY66BEJX 21:24 还在播、
  21:30 起 playurl -404 + wbi/view 62002，观众半分钟里从继续观看点了五次）才动手；`view` 说稿件还在时日志写
  `playurl 说 -404 但稿件还在 —— 是这一 P 的 cid（…）过期了，继续观看不动它`。
  **真在日志里见到那行，该做的是重新解析 cid，不是藏卡片**，别顺手改成藏。
- **充电专属（同一天）**：`BV19GM36GEno`（房房别闹）view 答 `is_upower_exclusive=true`、`is_upower_play=false`，app 端点强令牌
  答 `87007`，web 端点只给试看用的单文件，电视上两台镜像都 403。认得出来（view 那两个字段，或 87007）时：放不了说「这是 UP 主
  的充电专属视频，给 UP 主充电之后才能看」，试看能放时开头说一句只能看试看的一段（不说的话，试看放完像是应用断了）。
- **第三种 -404：番剧 / 影视的入口稿件**（2026-10-20，表现像闪退）。`BV1p64y1P7LJ`「【风骚律师】全系列上线B站！」是个
  普通稿件号，view 里带 `redirect_url = …/bangumi/play/ep813154`，真正的视频在 PGC 那套接口里，UGC 的 playurl 两种形式都答
  -404。以前先弹「已经被删除或下架了」再问 view，view 说稿件在就只写一行「cid 过期了」——话是错的，退回首页看起来像闪退。
  现在等 view 答了再说话，`redirect` 指向 `/bangumi/play/` 的再问一次番剧接口（`API.pgcAvailability`），屏幕上照搬 B 站
  自己的原因：「这是番剧或影视区的正片，B 站说：抱歉您所在地区不可观看！」；番剧接口说能放时才是「这个应用还放不了」。
  （第一版只说「这个应用还放不了」，用户点了第二次还以为是应用的毛病，而这一集在这里对任何客户端都不开放。）
  **番剧没接，是因为这里测不了**：`pgc/player/web/playurl?ep_id=813154` 从这个网络答 `-10403 抱歉您所在地区不可观看！`，
  官方客户端在这儿也一样。哪天有人要、又在能放的网络里，回答结构里的 dash 和 UGC 是同一种形状，接得上；但在那之前写出来的代码没人能验。
- **第四种 -404：点开时 view 就答 -404**（2026-10-26，1.4.10 起）。搜索结果、UP 主页这类没带 cid 的卡片，点开先问 view；
  一台香港、一台台湾的电视（都是 1.4.9）在搜索结果里反复点到 `wbi/view code -404 啥都木有`，屏幕上是接口原话
  「打开失败：wbi/view code -404 啥都木有」，每次都当出事传上来，日志里却没有一行说是哪个视频（`trouble()` 只有那句话）。
  两台都在港台，推测是搜索结果里混着这里看不到的稿件（也可能就是删了），没核对过 —— 没有 bvid。现在 -404 / 62002 说
  「这个视频看不了：可能已经被删除，或者在你所在的地区不能看」，`player:` 记一行 bvid 和标题，不算出事。
  下次再有港台的日志，拿那行的 bvid 从这里问一次 view，分得开「删了」和「这里看不到」。
- 这一层全程静默（卡片悄悄留下、或者悄悄消失，都不抛异常），所以在设备之外测：
  `tools/accounts-verify.mjs` 里那一节盖住了设备级、过期、`markAlive`、以及「记录必须
  活下来」。

**重开电视回到 App，首页会重取，光标回到「继续观看」（2026-08-15）。** Tizen 是挂起
不是杀进程 —— 同一件事让上报通道的失败计数能活过一整晚 —— 所以关机再开机回到的往往是
同一个 JS 上下文：昨晚的推荐还画在那儿、光标还停在昨晚看的那张卡上、`feedCache` 里还
是睡前取的那几页。现在离开超过**一分钟**再回来，就清掉所有标签页的 feed 缓存和服务端
历史缓存、重取首页，光标落回第一张卡（续播行画在推荐上面，所以就是「继续观看」的第一
张）。几处刻意的决定：

- **两路信号，因为这个固件到底发不发 `visibilitychange` 没测过**：一路是它，另一路是
  30 秒心跳发现自己**停跳**了（挂起时定时器冻结，迟到的那一跳本身就是证据，这一路能
  在压根不发那个事件的固件上活下来）。谁先到谁干活，60 秒去抖挡住另一路重复取。日志
  认 `lifecycle: 回到前台（visibilitychange）…` 或 `lifecycle: 心跳停跳（挂起过）…`
  —— **下次关机再开机就知道这台机器走的是哪一路**，别凭猜写死。
- **三处不动它**：正在播放（挂起中断的播放归播放器自己的阶梯管，底下换 feed 等于拆掉
  一个正要恢复的会话）、停在扫码页、停在账号页 —— 后两页正在问观众问题，替他答了比
  一屏旧内容更糟。
- **一分钟这条线**是为了区分「关机再开机」和「系统弹窗 / 瞥了一眼别的应用」：为后者
  把人家在网格里的位置拿走，比稍微旧一点的 feed 更糟。
- **唤醒这条路的首页加载失败会静默重试一次（3 秒后）**，不直接甩「加载失败」页 ——
  这台机器网络比屏幕晚几秒是有记录的（08-12 上报通道那次）。别的入口不变，失败照样
  当场说。日志认 `feed: rcmd 加载失败（…），3 秒后自动重来一次`。
- **开播也一样（2026-10-30 起）**：两种播放地址（dash / durl）**都**以 HTTP 0 或 network error
  失败 —— 请求根本没到 B 站 —— 时，1.5 秒后原样再要一次（不用预取的那份），屏幕写
  「网络不顺，正在自动重试…」；再失败才照旧提示「播放失败」、算出事。超时不重来（已经等了 20 秒），
  B 站答了码的（-404、-400……）也不重来。来由：马来西亚一台 Tizen 5.0（1.4.13），待机 1 小时
  47 分后回到前台（`visibilitychange`），首页重刷没报失败，7 秒后按播放，dash 和 durl 同一秒都回
  HTTP 0，上传了「拿不到播放地址」；观众隔一秒再按，同一个视频就放了。这条路**不限于醒来**：
  哪儿都是一次 1.5 秒的代价，真断网时只多等这一下。日志认
  `player: 两种形式都没连上（dash HTTP 0 / durl HTTP 0），1.5 秒后原样再要一次`。自测
  `连不上：打开一个视频，两种播放地址都回 HTTP 0`（`API._selftest.playurlDown(n)` 让接下来 n 个
  playurl 当场回 HTTP 0）。
- **服务端历史晚到时不只「补插」，内容变了也会重画**（`maybeRefreshResumeRow()`，按
  bvid+cid+进度算签名比对），条件仍是**观众没动过光标**（光标还在整页第一张上）——
  手机上刚看的那一集这才进得来。
- 挂起/恢复没有任何按键能复现，所以自测经 `window.__stWake` 进这条路，两步：
  `模拟关机再开机` 和 `醒来后首页重刷，光标回到继续观看`。它比对的是
  `window.__stItems` **换没换新数组** —— 只重画缓存会拿回同一份，那正是要抓的回归。
  2026-08-15 设备实测通过（`醒来：重取了首页，光标在继续观看第一张`）。
- **同一台电视两种行为都有，别把其中一种当成「这台机器的脾气」。** 08-15 当天一次
  关机再开机，日志里出现的是**一整套启动序列**（`whoami: 启动` / `engine:` /
  `account:` / 三行 whoami / `shaka 配置` / `update: 定时器到点`）—— 那是
  `window.onload` 从头跑了一遍，进程被杀了重启，没有可恢复的上下文，所以**没有**
  `lifecycle:` 那行是对的，这条路首页天生是新的。同一天下午另一次就是挂起（见下条）。
- **⟶ 挂起这条路当天下午拿到了第一份设备样本，而它证明两路信号的设计是必要的：
  `lifecycle: 心跳停跳（挂起过），离开了 10936 秒`（3 小时 2 分）—— 出来的是**心跳
  那一路，不是 `visibilitychange`。** 也就是说这个固件要么压根不发那个事件，要么只在
  回前台时发、没有配套的 hidden 可供计时（`hiddenAt` 是 0，离开时长量不出来，够不到
  一分钟那条线）。**两者的区别有意义**：后者说明事件可用，前者说明它不可用，所以
  visibility 分支现在会为「回到前台但离开时长量不出来」单独报一行
  （`visibilitychange 说回到前台，记到的离开时长只有 0 秒（一次 hidden 都没收到）`）。
  下一次样本里**日志一片空白**就是「这个事件根本不来」，**看到那行**就是「来，但只来
  一半」。**在此之前不要把心跳那一路当成冗余删掉** —— 目前它是唯一在野外真正生效过的。
  **⟶ 2026-08-17 这个悬案结了，答案是「两个都对，看走的是哪种离开」。** 当天两份
  visibility 样本，离开时长分别量到 **1 秒**和 **8 秒** —— 都是非零，也就是说 `hiddenAt`
  被填上了：**这个固件的 hidden 和回前台是配对发的，事件完全可用**。而 08-15 那次三小时
  的真挂起走的是心跳。合起来读：**被切到后台走 visibility 且配对完整，被挂起走心跳**
  —— 后台里定时器和事件照跑，hidden 配得上对；挂起时两者一起冻住，回来时补不出那半个
  hidden。所以两路都不是冗余，它们各自覆盖一种离开，**谁都删不得**；而且这两份样本同时
  说明一分钟那条线在做它该做的事（1 秒和 8 秒都没触发重刷，观众在网格里的位置没被拿走）。
  **判据是「后台还是挂起」，不是「离开多久」——这个标签当天差一点就写错了。** 头两份样本
  是 1 秒和 8 秒，几乎必然被概括成「短暂离开走 visibility」，而当晚 20:04 第三份
  `回到前台（visibilitychange），离开了 1088 秒`（18 分钟，时长照样量得出来）把「短暂」
  这个词直接否掉。同一形状的错误这份文档犯过一次（传输形状那条：判据是通道忙不忙，不是
  画面卡不卡）—— **一个碰巧与真判据相关的表面量，在样本少的时候看起来完全成立。**
  20:04 那份也是 visibility 这条路第一次真正越过一分钟那条线、走完整套重刷（前两份都在
  线下，只证明了事件配对，没证明后半段）。
- **醒来时正在播放，重刷是欠着而不是取消（08-15 同一份样本逼出来的）。** 那次挂起
  发生时电视上正播着视频，于是走了「正在播放，不动它」这条守卫 —— 而当时的写法里，
  这个重刷**再也不会补**：退出那个已经死了三小时的播放，回到的仍然是上午那份首页、
  光标还在老位置，正是本节要消灭的形状。现在 `wokeUp()` 记下 `pendingWake`，
  `stopPlayback()` 出口先 `payOwedWake()`，日志认这两行：
  `正在播放，先不动它 —— 退出播放时再补上重刷` 和 `退出播放，把挂起期间欠下的首页
  重刷补上`。**为什么是欠着而不是当场做**：播放期间发一批 feed 请求会和播放器抢这台
  机器本来就不快的链路（元数据请求要排到画面起来之后，是同一条老规矩），而且底下换掉
  feed 等于拆一个正要恢复的会话。自测里 `播放中来了一次挂起恢复` 那一步盖住这条路：
  播放中调 `__stWake()`、断言视频没被掀掉，退出播放后断言 `__stItems` 换了新数组。
- **在播放中拔电测这件事会什么都看不到，而且原因和这个功能无关。** 08-15 头两次
  测试就是这样白费的：断电时网络先没，播放器连抛几条错误把 `report()` 撞满五次，
  通道进五分钟静默，醒来那行正好落在窗口里被丢掉；`report()` 又是事件驱动的，静默期
  过了也得有新事件才有下一行。**测这条路之前先把播放停掉**，或者重装一次把计数器
  清零（`engine:` / `account:` 几秒内自己出现就说明通道是好的）。

## 续播点的第三个来源

**续播点还有第三个来源：`/x/player/v2`**（`API.playerV2()`），给这个账号在这个视频上的
`last_play_cid` 和 `last_play_time`（**毫秒**）。历史列表只有最近二十几条，所以基于它的
接力只在从「我的」点进去时有效；`player/v2` 对任何一条路进来的视频都答得上 —— 搜索
结果、推荐里的卡片、系列里深处的某一 P。它和两条 playurl **并排发**（`play()` 里
`got.dash/prog/resume` 三个都到齐才 `decide()`），所以不占到画面的时间；实测
`playurl=277ms` 没变。**它只在已经选定的那一 P 内挪位置** —— 选哪一 P 是
`resumeCid()` 的事，在这里改会把两个已经在飞的取流请求作废。超时 1200 毫秒后不等它。

有四件事合起来让这个列表看起来是坏的，而且全都是静默的：

- 「我的」先把本地列表画进 `#hist`，然后让 `API.history()` 把服务端列表画进
  **同一个容器**，直接覆盖。那时电视上播的东西还不进 bilibili 的历史，所以服务端
  一应答，在这台电视上看过的每个视频就全消失了。现在两份是合并而不是覆盖 ——
  同一个视频两边都有是正常的，合并按 bvid 去重、保留更靠后的那个进度点。
- `record()` 在位置低于续播阈值时把整条记录删掉，于是一个打开看了一分钟就离开的
  视频从来没进过历史。现在保留卡片，只丢弃位置。
- `ended` 事件上的 `forget()` 也会删掉整条，于是完整看完的反而消失。那个调用现在
  是 `finished()`，清位置、留卡片。
- **多分 P 的稿件总是从 P1 重新开始。** P7 的位置一直存着 —— 条目是按 `bvid:cid`
  存的 —— 但从来没有人问过它属于哪一 P。`Resume.lastPart()` 回答这个问题，
  `app.js` 里的 `resumeCid()` 使用它；只有当那个 cid 仍然是这个视频的某一 P 时
  才认，或者调用方根本没有分 P 列表时才认（推荐流的卡片只带第一 P 的 cid，而
  该 bvid 下存着的 cid 只可能来自播放过这个视频）。「我的」的卡片上带 `P7` 角标
  也是同一个理由：对一个 24 集的稿件来说，「看到一半」什么都没说。
